# 四期仓库验证进度

状态为部分验证。三期尚有未覆盖项，本期先推进与其独立的仓库页恢复边界；不宣称前序阶段已验收。

## 专用工作仓升级

本地 artifacts/workbay-upgrade-check 提取当前 Level、CanUpgrade、UpgradeStatus、BeforeRestoreNativeTabs、Upgrade、SetLevel、Resize，库存尺寸、物品和界面采用替身。九项断言通过：四次升级均使五页同步增加一行一列、每次扣一锭；满级不消耗；第三页 SetShape 抛异常后恢复此前已改页并保留锭；失败后重试成功且最后一锭销毁；读档恢复五页满级尺寸并阻止原版重置；原版仓继续原版恢复。

尚未覆盖 SetShape 的真实格位保留、回退自身失败、扣锭接口中途异常与普通水路由。生产源码未改。游戏手测每页右下角存物后扩四级、再存读档，核对物品格位和页签；满级继续拖锭不应消耗。

后续反编译目标版本 GameGridInventory：SetShape(int,int) 替换 inventoryShape 后调用 Validate；Validate 刷新像素尺寸、背景、格子及已有 items 的显示，不在该方法内移除、重排或重新装入库存物品。由此获得扩容保持集合的源码依据，但 item.Validate 的全部副作用及实际格位仍未实测。

普通水分流源码核对：IsRecipeWater 要求液体容器、WATER 类型及正水成分，排除酒容器、酒精、银血成分、花浆、基底油、还原剂和脂键剂。匹配后五页均允许，拖仓体固定选择食品页；其余配方液体分别按银血/香水成分接收。这里只读取标签，不改普通水身份、纯度或价值，也不接管原版顾客收货。此结论为源码层，尚未覆盖真实分类随倒装变化的场景。

## 阶段核查

### 改名回调会话保护

发现 CargoTabRename.Open 的 SetName 回调只检查对象销毁和所有权，未检查存档会话。本地 artifacts/cargo-rename-session-check 提取真实 Open、链接真实 StoreSession，保留仓库对象并递增资源代次后调用旧保存回调：修改前失败，旧仓名称被改写。增加打开时捕获会话及保存时 IsCurrent 判断后，相同场景通过，当前会话正常保存也通过。正式 Release 构建零警告、零错误。

该复现证明旧回调缺少隔离，不证明游戏中一定能在切档后保留可点击窗口。原版窗口和对象生命周期为替身，仍待游戏手测打开改名窗后切档/停用，确认旧操作不再写入；正常保存退出和双击改名应保持可用。

四期已有容量恢复、重复恢复、分类优先级、满页拒收、控制器查询缓存及配送后物品归属的局部证据。按照 AGENTS.md 和总方案仍为部分验证：固定价格与永久限购的仓库专用集成用例、五页完整允许清单、改名与规则跨档回调、旧占格受阻迁移、原版容器嵌套及游戏内存读档未全部覆盖。不能用这些局部检查宣布仓库工程完成。

## 分类路由

本地 artifacts/cargo-routing-check 提取当前 Rules、ParseFilter、RestoreFilters、Matches、Accepts 及完整 SortingRow，库存、归属和嵌套接口为替身。11 项断言通过：过滤页优先于较早通用页；首匹配页满时拒收、不转投后页；清空规则后使用下一过滤页；无匹配时用首个通用页；控制器、非自有物品、背包、不允许嵌套容器拒收；允许嵌套容器可进入通用页；仓内物品拖仓体不跨页；仓体不能装自身。

诊断有一条替身面板参数未使用警告，不是正式构建警告。本轮未改生产源码。真实容量布局、原版嵌套判定、多选分批放置及手动拖页仍待游戏验证。源码核对 AppendTab 给每页安装 Accepts 过滤，仓体路由与手动页接收共用该规则。

游戏手测：第一页通用，第二和第三页同时匹配烟酒，将第二页塞满后拖酒到仓体，应拒收；手动拖到第三页应可接收。清空第二页规则后再拖仓体，应进入第三页。控制器直接拖页应拒收、拖仓体应打开设置。

## 集装箱页恢复

本地 artifacts/cargo-restore-check 提取当前 CargoWarehouse.RestoreTabs，页签、标签与窗口采用替身。16 项断言通过：保存扩页值为 int.MinValue、-1、0、1、4、5、int.MaxValue 时分别恢复到限定页数，保留原首页与原标签；各场景再执行一次，页面对象及顺序不变；较小标签不会删除已有页面；原版仓与空对象不接管。

该测试不包含真实 AppendTab、过滤规则、页名绑定或 SaveManager 图节点挂回。因此仅证明恢复入口的追加与重复执行边界，不能证明真实物品保存恢复。未修改生产源码。

待游戏验证：扩四页，在每页边角存物并改名，保存重读，核对五页顺序、名称、物品及格位；再次存读保持一致。对照原版仓和专用工作仓，确认扩页模块拒绝使用且不消耗。

## 分类控制器补购与缓存

本地 artifacts/controller-stock-check 提取当前 ControllerAvailable、ResetControllerStock、IsLiveController，直接链接真实 StoreSession。12 项断言通过：无存量首次扫描；缓存期内复用；强制刷新发现新增实物；销毁或零数量不占额度；柜台子节点结果、拖拽中物品和待配送订单阻止补购；到期重扫；资源代次变化失效；扫描期间会话变化拒绝；缺公司状态拒绝。

源码核对 Services.PlaceOrderCore 在限购复核调用 Left 时传入 refreshControllerStock: true，因此该路径请求绕过目录显示缓存。尚未将真实下单与真实库存遍历接成同一个集成测试，不能把此源码判断升级为结账全链路已验证。

测试里的 GetAllItems 和 FindAllChildrenType 直接返回替身集合，未验证原版遍历深度。后续需要确认深层嵌套箱、未拆配送箱及多选拖拽物品的真实枚举范围。游戏手测在这些位置各保留一件控制器，打开目录并尝试提交，预期均不可重复购买；移除最后一件后可补购。缓存仅限查询期间的 0.75 秒，不作为提交放行依据。

### 目标版本原版遍历核对

重新反编译目标程序集中的 EmporiumEntry、GraphUtils、ItemMouseDragHandler、ItemMultiSelectHandler，输出仅保留在仓库外本地诊断目录。

- GetAllItems 枚举主库存、后库存、前库存、文件、展示柜、垃圾、隐藏库存、夜间窗口及两类售货设备；未枚举 backInvinvElementCounter。Mod 对后柜台的补充扫描有必要，不能直接删除。
- FindAllChildrenType 使用队列继续遍历 children，默认 passthrough 为 true；遇到 GameItem 不停止深入，因此已挂入图结构的容器内部也在枚举范围。它不证明未实例化的配送内容也存在于图中；待配送订单仍需独立检查。
- 单选 GetCurrentItem 返回当前拖拽物品。多选 StartGroupDrag 隐藏窗口并更新预览，不从原库存移除物品；CommitPrecisePlacement 才先 Expel 再 UncheckedAccept。稳定拖拽阶段仍可从原库存扫描选中物品，无需仅因多选就添加另一套扫描。

以上是目标版本反编译证据，不是游戏实测。放置提交过程中回调重入、未拆配送箱的具体图结构和深层箱实际打开/关闭状态仍待核查。本轮没有修改生产源码。

### 配送箱中的控制器

核对真实 Crates.CreateShell 和 CompanyVisitors.Deliver：箱体创建库存窗口，MakeOrdered 创建实际物品并经 Crates.Put 放入；只有 TryPlaceDelivery 成功且会话仍有效后才移除对应订单条目。并非开箱时才生成控制器。

在 tools/RestorationChecks/State 增加控制器专用配送场景，直接运行真实目录入口、配送和箱体代码：结算后订单为空、箱体已放置、箱内存在一件未销毁控制器，其 parentInventory 指向箱内库存。连同已有检查共 37 项通过。物品工厂、图节点及柜台仍为替身，新增断言验证结算后的归属关系，不证明任何中间回调都不存在暂态。真实图遍历与配送闭环还需游戏手测。
