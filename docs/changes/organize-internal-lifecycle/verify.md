# 验证与手测交接

## 当前状态

第零期自动核对见[F0 · 环境与接口证据](phase-zero-evidence.md)。第一期已实现模块状态、故障日志、快照和组合测试；本次实际运行记录见[F1 · 实施证据](phase-one-evidence.md)。M1–M6、P1/P2 待用户手测，未部署、未发布。

## 后续自动检查

在该期提交上执行 `./tools/Check-Maintenance.ps1 -GameManaged '<游戏 Managed>' -Dotnet '<SDK dotnet>' -Python '<Python>'`。要求检查全绿、两种构建零警告零错误、正式 DLL 的官方权限、拒绝和待生效均为零，且无维护输入。当前统一入口同时扫描正式与维护 DLL，两份均要求零权限；历史单扫描记录不能替代当前检查。新增测试应纳入同一入口，先 build 到当次独立 artifacts 目录，再由同一 SDK 直接运行新 DLL 的绝对路径。避免 `dotnet run --artifacts-path` 误用默认旧产物。改动检查入口时同时运行同参数的 `Check-MaintenanceContract.ps1`。

| 规格 | 自动证据 | 游戏证据 |
| --- | --- | --- |
| L1 | 快照无副作用、成功/未安装状态和失败降级 | M1、M2、P1 |
| L2 | 正式安装入口的部分失败、单项清理失败、日志或诊断失败隔离 | P1 验证正常启停；注入失败由替身覆盖 |
| L3 | 启停幂等、租约计数、其他监听者保留 | M4、P1 |
| L4 | 现有存档、支付、订单与隔离检查 | M2、M3、M5、M6、P2 |
| L5 | 原版事件替身的顺序、独立释放和重复安装 | P3 |

## 用户手测

第零期按[原 M1–M6 清单](../add-maintenance-interfaces/verify.md)操作，结果均待测。以下场景等对应阶段有可验产物再运行。记录日期、游戏版本、提交、DLL 类型及哈希和实际结果。用测试档副本。官方停用若只能在重新载入或重启后生效，记录真实路径和覆盖限制，不能据此判定热停用通过。

| 场景 | 已验证到 | 游戏里怎么看 | 预期看到 | 结果 / 日期 |
| --- | --- | --- | --- | --- |
| P1 第一期开店与启停 | 源码、编译、替身 | 维护版进测试档、开店并请求报告，关闭再开启恶意模式后再次请求；按官方入口停用、重新启用后再进档 | 模式开关不撤销登记；重新启用后 Malice 安装状态正常，三个事件各有一个该 owner，无重复日处理 | 待用户验证 |
| P2 第一期开店付款与换档 | 源码、编译、替身 | 旧测试档各完成普通订单和恶意模式代金券订单，尝试余额不足，保存后切另一测试档；正式版尝试热键 | 成功只扣一次，拒绝不扣，旧档订单和剧情正常，跨档隔离，正式版无热键报告 | 待用户验证 |
| P3 原版回调（暂缓） | 候选源码已读 | 使用有顾客及夜间服务的测试档，开店等待顾客并过夜，再经官方停启后重复 | 顾客与服务按既有条件触发，每次只处理一轮，无重复结算 | 待实施 |
| P4 条件抽取 | 待证据 | 同一测试档重复 P1–P3 并对比前两期结果 | 观察到的顺序、状态和数量一致 | 待实施 |

游戏里的故障频次、定位时间和性能数据目前为空。手测失败应保留操作与证据后回退对应阶段，避免借清档或重置进度恢复。
