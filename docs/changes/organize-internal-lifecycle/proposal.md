## 意图

面向公司增强维护者。资源阶段异常时，应能从稳定的模块名和阶段判断是安装失败、回滚遇错还是普通停用。重启后应能验证模块与其回调恢复到预期数量，并用真实安装入口的替身检查定位行为偏差。

| 已有能力 | 源码与尚缺的证据 |
| --- | --- |
| 官方入口已集中装配 | `Main` 通过 `RuntimeLifetime` 在获取前登记释放，`ResourceBootstrap` 依据资源就绪推进第二阶段，`Host` 隔离循环任务。启动日志指向总体失败，模块级安装状态与失败阶段仍缺统一的可读证据。 |
| 三个事件已有明确归属 | `ExtensionEvent` 返回租约，`OwnedCallbacks` 管理租约和旧委托，`Malice.Install` 已局部回滚，`ExtensionChecks` 已覆盖第二次注册冲突、重试、幂等和外部监听保留。诊断可枚举事件登记，安装整体结果与回滚失败仍须分别核对。 |
| 只读诊断和维护入口已具备 | `MaintenanceDiagnostics.Capture` 读取既有对象和计数，按存档与资源代次隔离故障，`Maintenance=true` 才启用 Ctrl+Shift+F10。失败回滚会清诊断且销毁输入宿主，须靠稳定的启动失败日志保留阶段证据。 |
| 付款和回归已接到正式实现 | `Services.Payment.cs` 已由付款及订单检查链接。前轮记录统一入口 24 步、正式和维护双构建、零权限扫描、三类失败入口；真实游戏 M1–M6 全待测。 |

这些是源码可见的维护缺口。现场故障频次、定位用时与长期运行成本尚无数据。参见[扩展字段清单](../add-maintenance-interfaces/extension-map.md)、[前轮实施证据](../add-maintenance-interfaces/evidence.md)和[历史反例](../../retrospective/README.md) A03、A04、B05、D04。

## 路线比较

| 路线 | 收益 | 成本与适用条件 |
| --- | --- | --- |
| 保留现状，随需求补接口 | 本轮只补 M1–M6，生产风险最低 | 模块级定位继续依赖源码和日志。试点收益无法测出时，回到这条路线。 |
| 轻量整理现有装配（推荐） | 先让一个模块的安装、回滚、卸载及诊断能整体核验。第二个模块提供抽取依据 | 有启停顺序风险。保持显式调用，每期只迁一处，允许一期结束后停止。 |
| 一次统一所有模块，或引入 DI、事件总线和插件注册 | 能统一表面接入形式 | 要重审回调顺序、返回值、Unity 生命周期及依赖扫描。现有消费者不足，回退范围大，不采纳。 |

## 范围与玩家影响

官方 IMod / Unity Mono / netstandard2.1，沿用现有 Harmony 实例及零权限要求。保持存档字段、ID、键、槽位、付款、剧情和原版业务规则。排除第三方扩展、插件发现与动态加载、全量委托事件化、额外玩家提示或彩蛋。玩家仍按原步骤存读档、开店和交易。内部状态仅从维护报告和现有启动日志获得。

本次交付是评审材料。进入代码阶段前需拿到 M1–M6 的实测记录，核对当前测试游戏版本的原版契约，并评审试点变更。第二个模块是否值得进入由第一期证据决定。官方停用可操作性及清理异常后的实际恢复行为保留为待验证项，详见[验证](verify.md)。
