# 内部框架建设总方案

2026-11-11 · 待评审 · 任务 [Issue #2](https://github.com/aamobe/CorpPresence/issues/2)

目标是降低公司增强新增功能、故障定位、回归与跨设备交接的成本。生产基线为 2500a6e；本方案建立在 46970f1 的设计文档上。现有诊断、三个具名事件、回调租约和 Malice 局部失败回滚作为基础能力继续使用。

## 总体路线

采用五个交付阶段，沿用已有零至三期编号，增加第四期收敛交接。第二、三期按证据进入，可以以“保留现有实现”的决策结束。整体属于内部维护建设，游戏玩法、存档契约及官方加载方式是验收约束。

| 阶段 | 核心问题 | 独立交付 | 进入条件 |
| --- | --- | --- | --- |
| 零期：环境与验收基线 | 当前版本和官方接口是否匹配 | 版本兼容清单、可复现检查命令、M1–M6 记录 | 可取得目标游戏及工具环境 |
| 一期：Malice 完整试点 | 模块是否安装，失败发生在哪一步 | 模块状态、阶段日志、真实入口测试 | 零期验收及首期设计评审完成 |
| 二期：原版事件接入 | 相同规则能否适用第二种接入 | Hooks 事件段的观察和启停证据 | 一期达标，第二模块有实际维护需求 |
| 三期：最小共用实现 | 哪些重复规则值得集中 | 一处已证实的共用逻辑或保留局部实现的决定 | 两处真实消费者和相同契约 |
| 四期：收敛与交接 | 下一次开发能否据此可靠接入 | 维护手册、模块接入清单、回归矩阵及交接记录 | 已执行阶段证据齐全 |

不以新增接口数量评估完成度。维护收益采用可复核事实，包括从一条失败日志识别模块与阶段、一次报告读取安装状态、重启后登记数量稳定，以及一次共用规则修改需要触及的调用点。耗时与性能缺少测量时保留空值。

## 当前架构及目标

Main 显式装配，RuntimeLifetime 持有运行期释放动作，ResourceBootstrap 判断资源就绪，模块内部持有自己的回调租约。Maintenance 按需读取值快照，tools 链接真实实现执行回归。

一期增加模块可观察状态；二期验证原版事件适用性；三期只抽取有重复维护成本的规则。付款与存档维持原契约，测试继续穿过真实生产入口。官方 Rev14 的 F9 面板、版本查询及结局接口先核对可用性，F9 面板不是一期依赖。详见[官方接口跟踪](../../maintenance/official-api.md)。

## 各期执行范围

### 零期

候选文件为前轮 verify.md、本目录 verify.md 及 official-api.md。核对程序集哈希、正式/维护产物身份与本机命令，运行 Check-Maintenance.ps1。按 M1/M2、M3/M4、M5/M6 分组由用户手测，形成版本及操作记录。

自动检查通过和游戏通过分别登记。真实游戏验收缺失时可以继续设计与只读盘点，代码试点按既有门槛进入。发现旧 DLL、环境错配或失败场景时，定位具体原因再重新验证。此期不引入游戏行为变化。

### 一期

候选文件为 Malice.Install.cs、MaintenanceSnapshot/Diagnostics/Formatter，以及 ExtensionChecks、MaintenanceChecks、RuntimeLifetimeChecks。详细字段、失败语义与 T1–T6 顺序以[首期详细设计](phase-one-design.md)为准。

先测试安装状态，再补失败路径、快照及所有权组合测试，最后做 P1/P2 手测。安装成功标志和释放失败标志分开；清理抛错后继续释放其他资源。重复停用及清理正常后的重启须保持登记稳定。完成门槛为模块和阶段可定位、报告只读、正式/维护隔离、对应游戏流程符合基线。通过回退本期独立提交恢复基线。

### 二期

候选为 Hooks.InstallEvents/UninstallEvents、Main 既有资源段及事件替身检查。先核对原版事件签名和时机，再测试部分订阅失败、外部监听保留和重复启停，最后采集与一期语义一致的状态。P3 验证顾客及夜间服务次数。

主要风险是重复处理或丢失原版事件。若共用要求迫使改变事件时序，停止提取并记录差异；回退只涉及本期提交。ItemRegistry 具有等待目录、激活与引用归属等额外语义，另立需求后再评估。

### 三期

候选为 RuntimeLifetime 和 Main 两个接入点。比较两模块的所有权、错误传播、状态及维护步骤。只有同一规则必须同步维护时才集中实现，先迁一个消费者并验证，再迁第二个。禁止把只省两次短调用当作新增抽象的理由。

完成门槛为同一规则集中维护、两模块真实入口回归及 P1–P3 对照通过。若收益不足，保留两处局部实现并写决策即可交付。回退抽取提交恢复前两期状态。

### 四期

候选为 internal-maintenance.md、源码地图、tools/README.md、当前变更的任务与验证文档。补一份基于已实施模块的接入清单，包含依赖、装配入口、回调所有者、释放动作、诊断字段、测试及用户验收；用另一名维护者可执行的步骤描述。

逐条核对需求与证据，清除过时导航，将未验证项交接到 Issue。检查文档链接、正式构建隔离和实际权限结果，记录提交身份及回退点。此期不强制新增第三个业务模块。失败则修正文档或回退本期文档提交。结束标准是新设备可从 Issue 找到下一步，且没有未提交的交接内容。

## 参考项目如何进入设计

| 来源 | 采用的原则 | 对应阶段 |
| --- | --- | --- |
| HugsLib | 生命周期每个入口明确触发时机，模块日志有稳定标识 | 零、一 |
| VContainer | 局部装配和生命周期内集中释放 | 一、二 |
| MessagePipe | 订阅租约、显式释放与订阅数量诊断 | 一、二 |
| Vanilla Expanded Framework | 多个真实内容模块形成共性，重命名与迁移显式评估消费者 | 二、三 |
| R2API | 按实际需求依赖功能模块 | 三、四 |
| NUnit | 参数化失败场景与每例状态清理 | 全阶段测试 |

查询日期、星数、维护与许可状态见[调研记录](research.md)。本方案采用设计原则，具体实现由本项目契约确定。

## 范围与决策

官方 IMod、Unity Mono、netstandard2.1 和零权限为目标环境。保留存档字段、ID、槽位、付款和剧情规则。排除第三方扩展协议、插件发现、动态加载、大型 DI 和新增彩蛋提示。模块状态只在启停变化，报告按需读取。

首期重点选 Malice、第二候选选原版事件段是方案建议。阶段工作量用任务和验收结果衡量，当前没有可信工期。任何新增接口先写明真实调用者、可变化依赖和失败契约；缺少依据时采用普通内部方法。
