# 分期任务

目标是用真实模块证明维护收益，再决定共用逻辑。评审入口见[提案](proposal.md)、[设计](design.md)和[规格](specs/lifecycle.md)。一期自动部分已实施，具体结果见[实施证据](phase-one-evidence.md)；游戏验收及后续阶段仍待完成。所有文件路径相对仓库根目录。

**全局约束**　官方 IMod / Unity Mono / netstandard2.1，沿用现有 Harmony 实例及零权限要求。保持存档字段、ID、键、槽位、付款、剧情和原版业务规则。排除第三方扩展、插件发现与动态加载、全量委托事件化、额外玩家提示或彩蛋。

**评审重点**　资源未就绪时采集状态，第二个租约冲突，清理抛错后继续释放，模式切换与停用区别，原版事件中其他监听者的保留。

## 第零期：验收已交付维护接口

**范围与前置**　以 `2500a6e` 的源码身份、正式和维护产物及可复制测试档为基线。文件候选是前轮 `verify.md` 及新增验收记录。此期只核对现状和回填结果，任何功能调整另开变更。

- [x] 核对游戏版本及两个 DLL 的构建身份，按[自动检查](verify.md)取得同一提交的新证据。
- [ ] 按 M1/M2、M3/M4、M5/M6 分批交给用户手测，记录操作、期望、实际及日期。开店与换档次数、报告中的 owner 数作为后续比较基线。
- [ ] M1–M6 游戏验收。用户已明确要求先进入一期代码实施；此项不标为通过，异常单独复现和归因。

**风险与回退**　混用旧 DLL 或测试档污染会产生伪结论。重新核对哈希并用独立存档副本复测。**独立成果**　有版本与产物身份的现状验收记录。

## 第一期：Malice 整体启停试点

**范围与前置**　第零期自动核对完成，用户已授权一期代码试点；零期游戏验收继续待测。涉及 `src/CorpPresence/Main.cs`、`Malice/Malice.Install.cs`、`Maintenance/MaintenanceDiagnostics.cs`、`Maintenance/MaintenanceSnapshot.cs` 和 `Maintenance/MaintenanceFormatter.cs`（后四项相对于 `src/CorpPresence/`），以及 `tools/ExtensionChecks`、`tools/MaintenanceChecks`、`tools/RuntimeLifetimeChecks`。保留三事件及所有支付、存档和剧情实现。无需新增统一注册协议。

- [x] 用真实安装入口及真实 `RuntimeLifetime` 验证未启用、安装成功、部分失败、停用两次、重启。复用第二次订阅冲突，另注入一次释放异常。断言失败后无本轮未释放租约（注入释放异常的资源单独记录），其他监听者保留，后续释放继续，重新安装数量不增加。
- [x] 给既有成功标志提供内部只读访问，在快照及格式化输出固定的模块状态。断言尚未进入资源阶段时读取不会触发初始化，成功时状态与三个 owner 一致，正常停用后清零。测试替身对真实 getter 或快照路径提供输入。
- [x] 在原有安装失败及清理告警路径携带固定模块名与阶段。故障注入证明日志可定位且原异常及清理顺序保留。维护热键由原宿主提供。
- [ ] 执行[第一期验收](verify.md)。进入下一期的最低门槛是一次故障可凭一条日志定位到模块及阶段，重启后登记数量稳定，正常游戏流程与基线一致。

**风险与回退**　影响保存和开店的安装链。回退本期独立提交，恢复原显式装配和诊断路径，使用同一份存档副本重新验证。**独立成果**　Malice 的模块状态、故障定位及生产入口回归证据。

## 第二期：物品接入流程与自动检查

2026-11-11 用户明确以物品扩展为主，并选择调整第二期。详细 I1–I5 任务、范围和结果见[第二期记录](phase-two-items.md)，接入步骤见[物品接入清单](../../maintenance/item-extension.md)。原版事件试点暂缓，前期游戏验收继续待测。

## 第三期：按物品需求提取共用规则

依据第二期检查结果和普通物品、设备、容器的真实接入需求，选一条具有重复维护成本的规则。可能是定义汇总或一致性校验，不预设通用模块类。至少有两个真实消费者、相同契约和可验证收益时才提取；否则记录保留现有实现。先细化当期计划，再改生产入口。
