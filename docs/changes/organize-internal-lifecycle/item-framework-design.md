# 物品框架完成范围

## 用户目标与顺序

用户调整顺序：先开发完物品框架，再提交一个实际物品需求。此前“暂无新需求所以暂不抽取”的决定只代表上一轮交付，不再阻止本轮设计与开发。后续真实需求用于接入验收；本轮以既有普通物品、设备、容器和状态差分作为兼容用例。

## 建议的交付边界

以下技术范围是本轮提出的方案，尚非用户已确认的具体设计。沿用官方 IMod、Unity Mono、netstandard2.1；服务于公司增强内部开发。

1. **定义汇总入口**：各生产线保留自身定义和业务实现，由一个内部目录汇总定义，记录来源并拒绝未经声明的重复键。Goods 使用该目录，不再逐处隐式覆盖。先确认当前合并中有无真实重复；合法覆盖必须明确记录来源和原因。错误包含键和来源，不静默接受冲突，也不注册半份内容。保持当前合法定义的顺序、值和创建时机。
2. **可检查的物品描述**：关联既有定义键、持久身份、文本键和资源引用，提供不创建 Unity 物品的只读检查视图。现有 ItemIdentity 仍是持久身份依据，GoodsText 仍是稳定文本键依据；检查视图从这些真实来源生成，不另造需要人工同步的第二份总表。身份与定义允许明确的一对多、公司工厂和状态变体，不能假设所有身份都对应独立 Goods 定义。
3. **接入完整性检查**：在构建后的统一检查入口中检验定义冲突、身份到创建路径的可解析性、所需文本键和自有嵌入图像是否存在。使用真实资源映射规则，不能用 LegacySprite 推导文件名。原版资源、共享图像、动态状态与可选文本必须通过具名规则说明，不用宽泛跳过列表。结构检查在开发时失败，不在玩家运行时全量扫描或引入额外权限。
4. **扩展与恢复边界**：继续通过 ItemRegistry 注册，通过 Goods.Make/Build 创建；Shell、Setup、OnNew、使用效果和读档恢复各有明确职责。生产设备、容器继续持有自己的库存、加工、升级和保存逻辑。提供普通物品、设备、容器及状态差分的接入说明，说明必须修改的位置、已有入口和对应检查。
5. **验证与交接**：把新增检查纳入 Check-Maintenance，并提供能拒绝错误输入的负例。保留 90 条已发布身份基线；不为绿灯自动更新。正式/维护构建与权限扫描继续执行，记录证据和仍需游戏验收的场景。

## 实现约束

不改变已有 ID、旧身份配对、存档字段、槽位顺序、配方、价格、付款、发货和剧情行为。不新增玩家内容，不加入第三方插件发现或动态加载。不承诺用一份声明生成任意设备的行为；设备专属代码仍需开发。

目录与检查视图必须能在无游戏启动的测试中读取。若当前静态初始化会触发 Unity，则将纯定义描述与游戏对象操作分开，测试穿过实际描述生产入口；不能复制生产字典或靠正则提取源码充当全链检查。不能以触发 Goods 初始化的反射读取绕过这一要求。

普通物品优先用 stamina，设备选已有实际加工设备，容器用 ProductionWorkBay/CargoWarehouse，状态用 candle/candle_lit 及运行态设备。它们是既有消费者，不新增演示物品混入发布内容。先验证当前定义集合，再迁移汇总，确保重构前后定义与关联一致。

具体内部类型名、文件拆分、检查视图的数据结构、负例组织和迁移顺序交由实施者决定并记入实施计划。既有专项检查仍按所改模块运行，统一入口通过不等于所有玩法都测过。

## “框架开发完成”的判据

- 所有现有定义经统一汇总；重复或不完整接入可以定位到具体物品和来源。
- 检查覆盖真实定义、真实身份表、实际文本键及嵌入资源，并明确列出合法状态变体和原版资源边界。
- 缺定义关联、缺必需文本、缺自有图像和重复键的负例被拒绝；既有内容及合法例外通过。
- 旧身份基线保持，生产构建零新增未解释警告，正式/维护隔离和零权限扫描通过。
- 新增普通物品、设备、容器各有明确接入步骤和验证入口；未来需求无需先寻找散落的注册位置。
- 代码、测试、文档完成并有本次证据。没有游戏实测时只能称开发及自动验收完成；后续物品需求仍需功能设计和实际游戏验收。

## 风险与回退

最高风险是静态初始化时机变化、状态差分误判、资源规则过严和旧身份被重写。按定义汇总、关联视图、检查接入分开提交；每一步保留兼容证据，失败回退该步，不修改身份基线或存档来掩盖问题。当前零至二期游戏验收欠项继续保留，不作为已通过事实。

确认此范围后编写实施计划并开始开发。推送、合并、部署和工坊上传继续遵循项目授权边界。
