# 公司 MOD 内部接口建设总方案

日期：2026-11-11。状态：T1–T6 源码与本地验证完成；游戏验证待用户执行。各阶段结果见 evidence.md。

> 执行时使用 `executing-plans` 逐任务实现。本文定义总范围、顺序和验收；[proposal.md](proposal.md) 定义需求，[design.md](design.md) 定义接口，[tasks.md](tasks.md) 给出 T1–T6 实施清单，[verify.md](verify.md) 记录游戏验收。以项目根目录 AGENTS.md 和《总方案》为开发依据。

**目标：** 优先降低我们自己开发、排错和回归验证的成本，建立维护诊断、内部功能扩展、测试接口三个相互配合的能力。

**架构：** 在现有会话、存档绑定、资源生命周期和付款入口上增量建设。查询返回独立快照；事件采用具名订阅及可撤销租约；测试直接调用正式业务实现，游戏边界使用替身。

**技术：** 官方 IMod、Unity Mono、Harmony、netstandard2.1 / C# 12；检查使用 .NET 8 SDK、PowerShell 7，现有恢复检查使用 Python；不新增 NuGet 依赖。

## 一、完成后能解决什么

| 方向 | 当前维护难点 | 本轮交付 | 可观察的收益 |
| --- | --- | --- | --- |
| 维护诊断 | 状态分散，日志不能区分未加载、保护、过期绑定 | 只读状态快照、故障聚合、维护构建报告入口 | 不修改存档就能定位问题处于哪一层 |
| 内部功能扩展 | 委托归属不直观，安装失败与释放难核对 | 三个生命周期事件的具名注册、租约、顺序及错误隔离 | 能列出监听者，验证重装无重复、释放不误伤 |
| 测试接口 | 部分测试复制业务方法，替身可能偏离游戏契约 | 真实付款入口检查、原生契约核对、统一检查命令 | 改动后能复跑关键路径，并知道哪些结论仍需游戏验证 |

不承诺“以后任何功能都无需改旧代码”。首轮只处理已有真实扩展点；新需求出现第二个实际使用场景后，再决定是否抽象。

## 四、目标 A：维护诊断

### A1 基线核查

建立完整的 Ext 字段表：类型、写入者、调用者、缺省值、失败策略、释放方式、钱货副作用。将已知支付契约明确为 null（未接管）、空串（接管成功）、非空串（拒绝）、异常（结果不确定）。

核对当前程序集版本/哈希及 SDK；运行现有生命周期、存档、订单、恢复、本地化、构建和仓库检查。已有失败原样记录，不能为了绿灯静默放宽检查。

### A2 只读快照

新增 `MaintenanceSnapshot`、`MaintenanceDiagnostics`、`MaintenanceFormatter`，均为 internal。

报告内容：版本、资源是否就绪和代次、存档绑定状态、公司及恶意模式记录的已知写保护、待配送订单张数、剩余物品条目数、资源缓存计数、近期故障、已迁移事件的登记者。

- 存档状态区分 NoStore、NotLoaded、Bound、Stale、Unstable。未知数量用 null，不显示成 0。
- 不调用 CorpState.Get、CompanyOf、Companies.StateOf，不创建玩家、注册物品、生成报价样品、加载图片或执行修复。
- 快照只保留值和复制后的只读集合，不保留游戏对象、委托、存档原文或可变字典。
- 采集前后复核 store、modData、资源代次及绑定。变化则返回 Unstable 并丢弃业务计数。
- `SaveBinding.Matches` 在原始字典为空时可能收养新字典；需新增纯查询路径，诊断不得调用会更新绑定的路径。原业务行为保持。
- 缓存计数由所属模块提供：Portraits、CatalogPricing、ItemRegistry。登记数量不冒充场景实物数量。

### A3 有界故障记录

原方案为最多 64 个聚合键。后续[评审修复](../../bugs/framework-review/assessment.md)改为运行期/会话各 64 个，分别保留前 16 个与最近 48 个；来源、阶段、错误代码、异常类型组成键；重复计数在 int.MaxValue 饱和。正文最多 4096 字符，来源等标识也要有限长，避免仅限制正文却让键无限增长。

只保存固定代码、异常类型和去路径/行号的调用链；不保留异常对象、Message、Data、存档 JSON 或 Exception.ToString。当前契约为切档清会话层，运行期故障保留至下一次启用开始；停用及启动回滚不立即清除运行期故障。记录和格式化失败不能改变业务返回值。

### A4 可用的维护入口

`Maintenance=true` 构建定义 MAINTENANCE，版本带 `-maintenance`，仅维护版支持 Ctrl+Shift+F10。按下沿触发、最短间隔 1 秒，通过现有 ModLog 输出固定 `[维护]` 前缀；不创建新 UI、不自动导出。

与 LocalTestFunds、WaterTrace 同时启用必须构建失败。正式/维护产物放不同目录，枚举类型及版本验证，禁止把维护版当正式 DLL 发布。

### A 的验收

- 无存档、坏 JSON、未绑定、过期绑定时查询不创建/写入/修复数据。
- 多次查询不改变字典、写保护、现金、订单或绑定；同 runID 换对象也能隔离。
- 返回快照不随原集合后续变化；采集期间切档不拼接数据。
- 容量淘汰、重复饱和、超长输入、无异常对象、输出异常都有用例。
- 正式 DLL 无维护触发器，维护版具备触发器，冲突开关被拒绝。

## 五、目标 B：内部功能扩展

首批只迁移 `BeforeSave`、`DayStart`、`StateReset`，不改 Charge、价格、门槛等有返回值的业务委托。

新增 `ExtensionEvent`：Subscribe(owner, callback) 返回 IDisposable；Publish 分发；Owners 返回只读登记者副本；Clear 撤销全部本事件登记。OwnedCallbacks 增加 Own(lease)，沿用逆序释放。

固定语义：

1. owner 必须是非空固定代码标识，同一事件内重复 owner 拒绝，旧登记不变。
2. 按登记顺序执行，每次分发取快照；分发中新增者下次生效，已撤销者本次跳过。
3. 同事件重入拒绝并记录，不递归执行；单监听者异常不阻断后续监听者。
4. Dispose 幂等；Clear 后旧租约不能删除新订阅；查询 Owners 不分发事件。
5. Malice 先用局部租约集安装，全部成功后才设置完成标志；失败只释放本次拥有的资源。
6. 保持每日业务顺序及每个原调用点只触发一次。存档切换和恶意模式开关不能误清运行期订阅。

故障隔离从“整个多播一次捕获”改为“逐监听者捕获”是本轮明确的行为调整，只适用于这三个事件，不套用到收费。

### B 的验收

覆盖 A/B 顺序、A 抛错后 B 执行、A 中增 C、A 中撤 B、重入、重复释放、Clear 后重装、第二个注册失败回滚、卸载后重装及无关租约保留。诊断器故障也不能改变这些结果。

报告只声称列出这三个事件的登记者；其余委托标为尚未迁移。

## 六、目标 C：测试接口和整体收尾

### C1 真实付款入口

将 `Services.Pay` 原样移入 `Services.Payment.cs`，仍为 Services partial 类；签名和本地化键不变。移动前后正文对比通过后再在已有失败分支加入诊断。

PaymentChecks 链接正式 Pay、CompanyMoney、SaveSlot 等必要代码；仅钱包、原生音效及其他游戏边界用替身。OrderChecks 删除复制的 Pay，接入相同真实付款入口。

验收：扩展 null/空串/拒绝/异常、先扣款后异常、零金额存档保护、余额不足、损坏记录、音效异常、诊断异常；订单提交重入、报价中换档、异常后解除提交锁。结果不确定不能解释为已回滚，也不能自动再扣一次。

### C2 原生调用契约核对

这次芒果电话问题表明：测试主动执行 startAction 会掩盖原版电话首句不执行它的事实。以后凡依赖原版回调，测试前必须记录当前游戏方法的调用顺序、是否触发首句、当前对象何时赋值、结束/中断如何处理。

测试使用正式业务实现，替身按已核对契约驱动；不能仅让替身按希望发生的顺序调用。反编译材料留本地，不入库。现有 MangoGiftChecks 的电话首句顺序作为防退化示例保留，不扩写新的彩蛋功能。

### C3 统一检查入口

新增 `tools/Check-Maintenance.ps1`，显式接受 GameManaged、Dotnet、Python，可选 OutputRoot；使用固定检查列表，不扫描执行任意工程。错误 SDK、缺引用、任一子检查失败必须非零退出。

串联仓库检查、正式构建、MaintenanceChecks、ExtensionChecks、PaymentChecks、OrderChecks、RuntimeLifetimeChecks、SaveStateChecks、恢复检查、本地化、双构建边界及官方权限扫描。输出每项名称、命令、退出码、证据层；日志放忽略目录，不生成压缩分发包。

### C 的验收

正式构建零警告/错误；官方扫描无拒绝、无待生效警告、无未知或未声明权限；所有必需检查成功；最终审查无阻塞问题；维护手册写清构建、按键、未知状态含义、事件清单、测试入口与人工场景。

## 八、风险、降级与停止条件

| 风险 | 处理原则 |
| --- | --- |
| 查询引发懒加载或状态修改 | 禁用该读取路径，补无副作用来源；无法安全读取则返回未知 |
| 采集中途对象或资源改变 | 不稳定快照，不返回混合计数 |
| 单监听者故障影响后续事件 | 隔离、记录、继续；收费不使用此策略 |
| 安装到一半失败 | 局部租约回滚，无关订阅不变 |
| 正式构建混入调试入口 | 双构建类型检查与冲突编译检查作为交付门槛 |
| 付款提取需要改变业务顺序 | 停止扩大抽取范围，保留现有方法契约 |
| 测试替身与原版不符 | 核对当前程序集契约，修正测试；无法覆盖的情况列为游戏验证 |
| 新增反射诊断触发权限 | 以实际扫描为准，缩减为固定错误码/类型信息，不扩大声明绕过门槛 |

不因接口工作引入第三方框架、全场景扫描、自动修复或玩法变更。必要范围变更要单独记录原因、替代方案及用户影响。
