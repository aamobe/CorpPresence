# 液体系统开发参考：原版扩展与独立系统

更新：2026-11-12。依据：用户明确决定、当前模组源码及已核对的原版程序集。本文是独立开发流程的参考和约束，不是生成器模板，不代表独立酒液系统已经实现。

## 最高风险声明与工具禁区

**水系统是本项目认定的原版最脆弱环节，按最高兼容风险重点对待。** 这是项目工程约束，不是对所有原版子系统做过量化比较后的排名。原版水名、分类、成分、纯度、鉴定、价格、顾客收购、倾倒与保存彼此关联；修改一个入口可能影响其他原版物品和既有存档。

**新物品开发工具禁止参与新液体设计或实现。所有新液体必须走独立开发流程。** 限制同时适用于“扩展原版水系统”和“独立液体系统”，不因某条路线看似简单而放行。

工具不得：

- 设计液体成分、含量、配方、反应、品质、酒精度或交易规则。
- 生成或应用新成分注册、液体容器初始化、灌装/倾倒/混合、加热/过滤/蒸发、液体存档迁移和交易代码。
- 生成液体实现骨架、示例配方或默认参数，再把未完成的风险转嫁给使用者。
- 用普通物品入口生成带液体身份的半成品，或将液体转换成普通商品登记来绕过限制。
- 通过自动修复、代码注入或额外补丁改变原版水名、水分类、水价、成分定义或顾客行为。

工具只允许识别请求触及液体边界，给出拒绝原因和本文链接；不能为用户选择路线、自动推导方案或创建目标代码。Preview/Apply/Check都不能把不支持的液体输入报告为成功。独立开发人员仍可直接使用仓库已有编译和回归脚本；这是开发验证，不是授权生成器设计新液体。

这一约束不能被“高级模式”“强制”“仅生成草稿”或未知类型回退绕过。本文后续的技术字段供独立开发审查使用，不是工具输入模板。

## 1. 先区分事实、工程决策和待验证项

| 类型 | 内容 |
| --- | --- |
| 原版源码事实 | water是一种成分，WATER是商品分类；带基础价格标签的非空液体容器会被原版归为WATER |
| 现有项目事实 | 银血使用原版液体容器和注册成分；分类修复继续维持这一既有路线 |
| 用户确定的设计原则 | 按多成分、多含量配方设计的调酒玩法采用与原版水系统并行的独立液体系统，不能只在原版水容器上增加酒类标签 |
| 工具边界 | 两种路线的新液体都禁止自动设计/生成，必须进入独立开发流程 |
| 尚未实现 | 独立酒液状态、容器交互、交易、持久化和跨系统转换；本文不是实现或实测证明 |

不要将“参考原版成分模型”写成“沿用原版water运行路径”，也不要将“独立液体系统”理解为修改或复制一份全局WaterHelper后覆盖所有水物品。

## 2. 两条路线的选择与责任

| 方面 | A：扩展原版水系统 | B：独立液体系统 |
| --- | --- | --- |
| 适用目的 | 明确希望新增成分参与原版水的混合、纯度和既有处理流程 | 希望液体具有独立配方、名称、品质和交易语义，例如调酒 |
| 核心状态归属 | 原版容器与原版成分状态；扩展只拥有自己的注册项和特定规则 | 自有成分、配方和容器状态；复用通用物品框架不代表使用水容器能力 |
| 非空分类 | 接受原版WATER动态分类及其关联行为 | 不进入WATER自动分类链，由独立系统维护合法类别 |
| 成分注册 | 必要时向原版表追加有命名空间的新ID，不能覆盖已有条目 | 使用自有成分标识与状态，不默认注册进Liquid.Liquids/LiquidDict |
| 名称、品质与价格 | 不为自有内容改写原版全局水名、等级或价格；扩展范围必须明确 | 独立名称、配方判定、品质与估价；不能回退成原版水价 |
| 保存与恢复 | 核验原版状态实际保存和自有成分注册时序 | 独立设计持久字段和恢复过程，可以评估原版通用保存载体，但不能依赖未核实的水恢复入口 |
| 顾客交易 | 服从原版收购和拒收；WATER不是任何顾客都会买的保证 | 明确买家、资格、报价和结算入口，不能仅加标签就宣称可交易 |
| 倾倒互通 | 使用原版已支持的路径，验证自有成分是否被正确计算 | 默认不与原版容器直接互倒；若需要，单独设计显式转换协议 |
| 工具支持 | 禁止设计与生成；转人工独立流程 | 禁止设计与生成；转人工独立流程 |

A不是B的快捷实现。若需求要求“不同配方按酒价出售、不能被识别为水”，则以B设计，不要先按A制作再通过改水名、删WATER或强加酒标签补救。

一件实例在同一时刻只能有一个液体状态所有者。不得同时让原版水回调和独立系统修改同一组含量、分类或价格。

## 3. 已核实的原版耦合点

核对程序集SHA256：`725CB999D019DFF1FF31BED353C7F9BB8D81A7605A15DE1F80F5A3A6CF7B1D05`。游戏更新后应重新核对实际使用的方法；不将旧结论自动套到新版本。

- `WaterHelper.GetWaterPurity`：water成分量×10000÷全部已注册成分总量；因此自定义成分也会影响分母。
- `WaterHelper.GetTotalVolume`：遍历Liquid.Liquids，读取对应currentPart。存档中有标签但注册表缺项时，这条计算路径不会计入它。
- `WaterHelper.UpdateContainerGoodType`：存在液体容器基础价格标签时，空容器走HOUSEHOLD_GOOD，非空走WATER；不是按“是不是酒”的配方判定分类。
- `WaterHelper.InitLiquidContainerItem`：初始化容器能力并将当前成分量置零，不能随意用于已恢复内容的对象。
- `WaterFeatureHelper.OnLiquidChanged`：联动分类、真实/表观纯度、等级文字、价格和试纸状态，不是纯粹的UI刷新函数。
- `SaveManager.EncodeNode/DecodeNodes`：保存状态及分类，读档先调用工厂，再恢复保存值；恢复之后的模组修复仍可能再次覆盖分类。
- `StoreClient.IsClientBuyingThisItem`：先判断拒收，再检查收购ID、标签和偏好；不能概括成固定“WATER永远优先”，但进入WATER路径会把物品暴露给原版水分类及相关定价/处理规则。
- `WINE_CONTAINER_TAG`等原版专门分支存在，但名称包含wine并不能证明满足独立调酒需求，必须核对调用链，禁止未经核对将其当快捷开关。

上述方法具有状态副作用。UpdateContainerGoodType在特定背包条件下还会刷新事件特性，读取缺失标签也可能创建默认值；不能把它作为独立系统的通用分类辅助方法。

## 4. 银血反例与当前修复的适用范围

**用户提供的历史教训：银血早期开发曾修改水名并引发一系列问题。** 本文记录这一反馈作为禁止全局改名的依据；尚未逐一还原当时所有提交和故障，不能声称已证明每个故障都由同一处改名引起。

当前银血仍属于路线A：在原版成分表注册粗异构蛋白和异构蛋白，容器沿原版液体能力运行。初始50mL配方中water为28mL，所以按已核实公式水纯度为56%；这不是独立酒液系统的模板。

另一个已经定位的代码问题是：静态Types只有MEDICAL，读档后的标签修复清除WATER；已通过委托原版恢复空/满分类修复，见[修复记录](../liquid-classification-fix-2026-11-12.md)。它与历史水名改动是两件事，不能合并成一个已验证根因。

当前ItemTags.Apply只要看到LIQUID_CONTAINER_TAG就委托原版分类。因此未来独立系统不能通过沿用此标签或原版液体壳体再删除WATER来实现隔离，否则下一次创建、刷新或恢复可能重新进入水路径。也不能因制定路线B就批量移除现有银血的标签、改ID或迁移旧档；那是另一项需要专门设计的变更。

必须避免：

1. 改原版water定义、水名、全局本地化变量，让全游戏的水替自定义配方显示名称。
2. 将所有含自定义成分的容器强制从原版水体系抢走，影响玩家原有混合物。
3. 给同一容器同时挂原版水与自有酒液处理，让两套系统争用状态。
4. 用静态酒类标签对抗原版动态WATER刷新；只在初始化时删一次WATER也无效。
5. 按显示名称判断成分、品质或物品身份；切语言和重读档后名称不可靠。
6. 在读档修复里重新初始化、灌满容器或重套默认配方，覆盖玩家调配结果。
7. 将“可以保存一个对象”“看见酒名”“能卖给某个顾客”当作完整兼容验收。

## 5. 独立液体系统必须独立完成的设计

以下都是独立项目的交付要求，不是本次授权开始实现新系统。

### 成分、计量和配方

- 使用稳定命名空间ID，不用显示名做键；成分清单、数据版本与已知依赖明确。
- 体积单位、整数精度、最大容量、溢出保护、比例计算和取整余量必须统一。建议评估整数微升，但最终单位须由独立方案确定。
- 混合必须保留各成分真实量；配方识别是从组成推导，不能用一个“酒种标签”替代实际组成。
- 酒精度、糖分、品质、污染、成熟度等属性分别注明是否支持及计算来源，不凭常识默认原版已提供。
- 配方允许区间、最小量、冲突优先级、混合后失配行为必须确定；未知配方也要保留成分，不清空或自动补齐。
- 明确哪些性质按体积混合、哪些必须额外保存；陈化时间、来源或鉴定结果不能未经设计直接平均。

### 容器、操作与状态转换

- 独立壳体的身份、容量、空瓶类别、满瓶类别、开封/密封、堆叠与不可堆叠条件明确。
- 新建空壳、首次灌装、读档恢复分开；恢复不重跑首次奖励/灌装。
- 对加入、混合、部分倒出、排空、灌装、拆封、加工、摔坏等实际支持的操作逐项列触发条件、消耗、输出和失败结果；不支持的交互直接拒绝。
- 新液体不自动继承原版水培、养殖、饮水或净化能力；是否接入这些消费者，分别设计。
- 外观、名称和类别从本系统状态刷新；变化后失效旧估价缓存，禁止通过改全局水资源更新自有物品。
- 定义销毁和取消交互的资源归属；异常不留下已扣液但未交付的半操作。

### 交易与估价

- 原料价值、配方溢价、品质、容量、容器价格、开封折价及违禁条件分别定义；列出每种规则唯一负责的代码入口。
- 公司订货、普通顾客、特殊顾客、售货机等渠道分别标支持/不支持；不是所有渠道必须实现。
- 明确是否按当前真实配方或已鉴定信息报价，何时允许拒收；不借用原版水的表观纯度替代酒液鉴定。
- UI报价与扣款/成交再次校验同一组成版本；报价后混入新成分、换容器、换档时旧报价失效。
- 确认不会触发水价、水等级和模组售水合作奖励；这需要查交易入口和相关补丁，不能靠“没有WATER标签”一句话代替证据。

### 持久化与兼容

- 保存结构必须含版本、成分量和影响玩法的其他状态；配方名等可推导内容不作为唯一恢复依据。
- 明确写入原版通用item state还是自有mod数据及其生命周期，实际验证序列化/反序列化，不仅验证内存对象相等。
- 读档顺序、复制/拆堆/合堆、库存嵌套、交换场景、切档与模组启停逐项列出状态所有者。
- 未知成分、版本更高、缺依赖时保留原始数据，限制危险操作并报告；不得以空瓶或默认配方覆盖。
- 迁移只作用于明确自有身份，保留玩家比例、数量和改造；重复执行不产生额外物品。
- 卸载模组后是否能读档、重装后是否能恢复需如实说明，不能保证独立ID缺失时原版一定安全回退。

## 6. 两套系统之间只能显式转换

默认禁止原版容器与独立容器直接互倒。不支持转换时应提示原因并保留源内容，而不是让原版交互接管。

确有转换需求时，独立流程必须写出方向、允许的源/目标身份、成分映射、单位换算、未知成分策略、容量、附带状态和损耗。导入原版水不是只取water而静默丢弃其他成分；未知或不可映射成分必须保留或拒绝，不生成假定纯水。

执行顺序：校验源与目标及会话 → 准备映射与输出 → 再次检查容量和状态版本 → 按可观察的转移结果提交双方数量 → 更新各自的显示/报价。失败或重复回调不能复制、吞掉液体；原版路径不能保证原子回滚时，应限制转换方式并单独验证，而非假定try/catch已经回滚。

反向转换同样需要设计。不能将原版瓶子临时加上独立标签就变成新系统容器，或把独立瓶子加LIQUID_CONTAINER_TAG作为万能兼容方案。

## 7. 强制独立开发流程

1. **需求边界**：列出实际操作、交易渠道和保存要求；开发者与用户确认路线A/B。调酒按本次用户决定走B。
2. **原版与模组源码核验**：记录游戏版本/程序集指纹，逐条追踪分类、名称、价格、保存、交互；不得仅按方法名猜测。列出会被当前ItemTags及其他补丁识别的条件。
3. **独立设计**：提交状态模型、操作时序、所有权、交易规则、兼容和失败处理；水相关行为与存档字段变更在对应文档先写清。
4. **隔离试点**：最小自有身份和最少操作；不修改原版默认数据，不在正式存档试验，不把试点产物自动加入发布目录。
5. **必要代码检查**：先覆盖实际风险再实现，日常只跑受影响的检查；不能为了快省略成分保存、交易隔离与失败不丢量这些关键项。
6. **最后统一回归与最小实机**：验证独立流程和原版对照；出现跨系统影响先修复，不以修改全局水规则绕过。
7. **独立交付审查**：确认未污染原版定义、没有双重状态所有者、未包含测试物品；保存提交与DLL对应关系。提交GitHub、部署和发布分别按项目授权执行。

工具提示转入该流程，不等于开发工具已经完成设计，也不等于独立开发必然无风险；通过分离责任和明确验证降低风险。

## 8. 验收矩阵

| 检查 | 路线A | 路线B | 证据要求 |
| --- | --- | --- | --- |
| 原版回归对照 | 原版水名、等级、价与收购不被自有配方改写 | 原版水全过程不受独立系统影响 | 原版水瓶对照，必要代码与实机 |
| 状态与计量 | 自有成分参与原版计算，无重复注册/清空 | 混合、分装、取整、空满、未知配方均保留量 | 真实业务逻辑测试 |
| 分类隔离 | 维持原版WATER与空瓶规则 | 各生命周期节点不被水分类/水价路径接管 | 入口核验、定向测试、代表场景实机 |
| 保存恢复 | 注册顺序、成分标签、鉴定状态 | 独立数据版本、比例、质量和容器状态 | 实际序列化与读档验证 |
| 交易 | 原版合法顾客与水相关奖励行为符合需求 | 指定酒类买家/报价正确，水奖励不误触发 | 订单/成交代码检查及一条真实交易链 |
| 跨系统转换 | 仅检查实际支持的交互 | 未实现则拒绝；实现则检查守恒/损耗、容量、失败重试 | 转换专项，不自动扩大范围 |
| 工具拒绝 | 不生成新成分/容器/配方 | 不生成酒液系统或实现骨架 | 输入拒绝且仓库字节不变 |

## 9. 混合类别也不能绕过禁区

以下请求即使kind写成普通物品、植物或设备，也必须被工具拒绝设计/生成：新植物产出新液体成分；新药剂需要液体组成或纯度；新设备含新液体配方/反应；容器要求自动灌装、倾倒或保存新液体；独立酒液成品要求配方身份或跨系统转换。工具不能先生成其中一半，让剩余液体行为成为隐藏待办。

仅制作空的普通装饰瓶且完全没有液体能力，可按普通物品处理；涉及现有液体的设备也不得自动生成液体操作，应人工核验。独立人工设计与验收通过以后，不自动解除生成器禁令；未来如要支持，必须另行改变本原则并重新审查。
