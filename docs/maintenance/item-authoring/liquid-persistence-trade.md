# 液体保存与交易专题（人工独立开发）

水系统是最高兼容风险，原则见[主参考](liquid-systems.md)。没有工具生成入口。

保存链：GameItem.ModifyTag写state→SaveManager.EncodeNode克隆state及分类→读档先目录工厂创建→恢复保存state/modifiedState等→模组限定身份的修复。读取GetTagReadonly返回副本；只改这个副本不能持久保存。成分注册必须在使用原版总量/恢复逻辑前就绪。注册缺失、模组移除和旧版本字段迁移分别设计，不宣称原版自动兼容。

交易链：顾客先拒收，再看收购ID/标签/偏好；已核实的具体条件见[原版契约](native-contracts.md)。WATER分类不保证顾客收货，显示为“酒”也不保证按酒价卖。模组售水奖励另要求WATER且水纯度大于0，它不是顾客交易完整判据。

人工需求需分别写明空壳价、体积价、品质/鉴定影响、柜台/售货机/售水机资格、公司奖励、实际结算与失败重试。路线B必须独立拥有分类与估值，不通过原版全局水名或水价补丁实现。路线A则必须接受并核对原版耦合。

状态转换：新建默认→内容改变→鉴定/价格刷新→保存→恢复→交易资格复核→成功结算。每阶段列唯一权威状态和消费者；派生价格、真实/表观等级、试纸标记不能混作永久组成。原版OnLiquidChanged还会清理试纸标记，不是单纯UI刷新。

反例：静态Types修复清掉WATER，造成新建与读档分类不同；新增酒标签却继续依赖原版水估值，卖出价格仍服从水链。前者是已有银血分类修复的适用问题，后者需路线B专案，不能混成一个补丁。

必要代码核验含量持久写入、注册时序、迁移幂等、静态修复与动态分类、拒收边界；专案实机选择一个自定义样品及原版对照，保存重载后检查组成、等级、价格与符合条件的收货。未做的层必须如实标注。
