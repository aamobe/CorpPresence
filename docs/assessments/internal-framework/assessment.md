# 接口与物品扩展框架完整评估

评估日期：2026-11-11（Asia/Shanghai）。当前源码基线：`4decdcd`，已合并 main。对象是公司增强自身的开发维护能力；本报告不修改运行时代码，不启动后续阶段。

## 结论

当前最明确的收益是：部分错误能在提交前被发现、模块失败更容易定位、跨设备交接更明确。对新增物品开发速度的收益，目前主要来自清单和检查，尚没有实际内容开发对照数据。运行性能、玩家故障率和维护耗时的改善均未量化。

它适合称为“已有运行基础上的维护与回归检查体系”，尚不宜称为完整的物品开发平台。零/一期和二期的游戏验收仍有缺口，第三、第四期尚未实施。值得继续投入，但下一步应围绕真实物品需求验证收益，不以框架类、接口或文档数量作为完成标准。

## 1. 范围、方法与证据强度

“接口”分为游戏官方 API，以及项目内部的生命周期、事件、付款和诊断约定。“框架”包括运行期装配、物品接入流程、测试工具、基线和交接文档。三者的收益和成本分别评估。

本次核对了 Main、RuntimeLifetime、OwnedCallbacks、Ext/ExtensionEvent、Malice 安装器、维护诊断、ItemRegistry、ItemIdentity 检查器、Goods 定义汇总、付款入口、统一检查脚本、Git 历史和发布记录。使用 codebase-design 的判断原则：调用者是否少掌握了一项复杂规则、改动是否更集中、测试是否经过真实入口；不按类数量打分。

| 证据级别 | 本文如何使用 |
| --- | --- |
| 当前源码/历史差异 | 支持“有什么机制、改变了什么”；不直接证明游戏表现 |
| 已提交执行证据 | 引用当期实跑结果，明确其提交和替身范围；不是本次重新跑出的成绩 |
| 本次静态核验 | 检查源码结构、历史归属、文档链接和差异；提交前执行仓库检查 |
| 推断/预期 | 用“可能、预期、待测”标明，并提供验证方法 |
| 尚无证据 | 不给性能倍数、节省百分比、故障率或综合分数 |

本次是评估文档任务，未重新运行构建、26 步套件、官方扫描、游戏或发布核验。既有最终运行记录见[F2 · 第二期证据](../../changes/organize-internal-lifecycle/phase-two-items.md)：26 步、41 条物品断言、双构建零警告零错误、双版本零权限扫描及三类入口失败检查通过。26 是检查步骤数，41 是顶层断言数，90 是身份记录数，均不是代码覆盖率。

## 3. 多维度评估

以下“收益较明确”指机制与检查证据，不等于玩家故障率已下降。

| 维度 | 实际帮助 | 成本、局限与判断 |
| --- | --- | --- |
| 官方 API 适配 | 按实际程序集核对签名和时机，避免把 beta 文档当作已安装能力 | 仍需逐游戏版本维护；现有本机缺少新版版本查询/F9/结局接口，不能计算其潜在收益 |
| 生命周期 | 显式装配、释放归属、部分失败回滚，便于追踪启动过程 | 主要验证 Malice；清理动作抛错后会被清空，报告失败不等于自动恢复 |
| 事件组合 | 三个具名事件能独立取消订阅，保留外部监听，隔离单项异常 | 其他 Ext 委托仍是静态字段；不是所有扩展点都支持多消费者或同等隔离 |
| 故障定位 | 固定模块/阶段、安装与清理状态、只读快照缩小排查范围 | 故障聚合有界并会按会话重置；启动回滚后仍要看日志；没有定位耗时对照 |
| 普通物品开发 | 明确 Goods、身份、目录、文本和获取入口；身份修改有自动阻挡 | 多处信息仍需手动对应，还不是“一份声明即可接入”；速度提升未实测 |
| 设备/容器开发 | 复用基础注册、身份与已有付款/保存检查 | 加工、空间、耗能、子库存、槽位和恢复逻辑高度具体，无法由通用注册器保证 |
| 旧档安全 | 保护已有身份映射，检查准确配对、未知身份拒绝、重复迁移边界 | 不覆盖全部标签、JSON 结构、槽位顺序、原料、基因与剧情；不能称为完整存档兼容框架 |
| 付款与订单维护 | 测试链接真实入口，减少“模型通过而生产代码不同”的风险 | 游戏钱包、UI、音效和交付环境仍含替身；不能推广为跨所有操作的事务系统 |
| 回归与重构 | 已有契约可反复执行，帮助保护局部改动 | 覆盖没有百分比数据；仅有本地统一入口，不是每次 push 自动强制执行 |
| 跨设备协作 | 提交、方案、已测/未测状态集中到 GitHub | SDK、游戏依赖、部署副本与存档仍需准备；尚未证明第二台设备干净复现全过程 |
| 性能与内存 | 快照按需读取；故障记录限制 64 项并使用弱会话引用 | 正式版也保留诊断核心，发生故障会采集调用链；没有帧率、GC、加载或长时运行实测 |
| 隐私与权限 | 新的生命周期警告不包含异常消息，诊断不保留异常对象或源码位置；双版本扫描有证据 | 部分旧日志仍拼接异常 Message；零权限扫描不是完整隐私或安全审计 |
| 发布可追踪性 | 发布记录、源码身份、哈希和测试证据可以对应 | 多次产物沿用 1.1.0，不能只看版本号判断实际内容；上传回执也不替代游戏验收 |
| 可扩展性 | 继续沿用显式装配，没有引入额外加载器或大型依赖 | 类型普遍 internal 且依赖静态游戏状态，不是可供外部 Mod 稳定调用的 SDK |
| 学习与 AI 辅助维护 | 接入清单、源码地图和失败契约减少猜测入口的机会 | 文档重复和失效会反过来误导；没有多人接手或 AI 返工率的统计 |

## 4. 实现层面的得失

### 4.1 值得保留的设计

Main 把核心阶段和资源阶段显式分开，RuntimeLifetime 先登记释放动作再获取资源；调用者可以看到装配顺序。现阶段没有理由再套一个只转发这些调用的通用模块层。

ExtensionEvent 只处理主线程生命周期通知，没有被拿来合并付款结果。付款扩展的 null、空字符串和非空错误字符串分别具有不同语义，异常时结果可能不确定；把它强行改成普通广播事件会损害原契约。

MaintenanceSnapshot 保存不可变值与只读集合，采集不稳定时返回未知，而不是将未知当成未安装或零订单。这提高了报告的可信度，但没有修复被报告的业务问题。

ItemChecks 将两个证据层分开：注册器以少量替身身份输入测试真实生产入口；身份检查读取本次编译 DLL 的真实表与 ResolveId。固定基线不会在每次运行时自动更新，负例验证了部分检查器拒绝行为。这比复制一套生产逻辑再测试复制品更有价值。

### 4.2 尚未降低的开发复杂度

Goods 仍同时承担定义汇总、构造、图像、形状和使用等职责；Hooks 仍容纳多类补丁和事件入口。当前文件长度分别约 1643 和 893 行，只用于定位阅读成本，不据此判定必须拆分。新物品仍需理解多个文件和调用时机，增加接口不自动消除这些知识负担。

Goods 汇总多条生产线定义时使用字典索引赋值，后写同键会替换前值。这是代码行为，尚未证明当前存在重复键。身份表唯一性检查不能发现定义在汇总前已被覆盖；“所有物品定义一致性已经验证”因此不成立。

静态类型、游戏对象、业务规则和展示数据仍有较强耦合。现有独立测试通过替代游戏边界解决部分可测性问题，不能据此认为业务已经全面解耦。任意引入依赖注入也可能让配置成本大于收益。

## 6. 后续开发场景的实际帮助

**增加普通消耗品**：当前清单能帮助找到定义、身份、文本和获取入口，基线可防止误改已有 ID。但漏加 Goods 定义、缺贴图或商品不可获得仍可能通过当前身份检查。适合作为第三期第一个收益验证场景。

**增加加工设备**：注册与身份部分可复用；原料、电力、产物空间、部分成功、升级和读档恢复仍需专属设计与测试。不要用“可注册”代替“可生产”。

**增加容器或扩页模块**：已有框架不能自动保证槽位顺序、嵌套对象和旧库存保留。风险明显高于普通物品，不能把普通物品的模板直接当完整验收。

**修复支付或换档问题**：已有真实入口回归能缩小修改范围并保留复现，但必须先确认故障版本、会话与原生行为，不能因套件通过就排除业务错误。

**升级游戏或接入新版官方 API**：当前签名核对、扫描和证据记录能帮助定位影响范围；仍须重新核对目标版本。新版 F9 等接口目前仅属候选，不能写成已交付价值。[接口跟踪](../../maintenance/official-api.md)

**第三方 Mod 扩展或多人同时开发**：现有方案未承诺公开协议、版本兼容或并发注册。可以改善本项目交接，但没有证明已经适合外部生态或并行内容包。

## 7. 投入收益、替代路线与停止条件

维护总成本包括框架实现、测试与替身维护、基线审查、文档同步、构建环境和游戏验收。只有避免的返工与重复工作超过这些新增成本，才构成净收益；目前没有足够工时数据计算回本时间。

| 路线 | 适用条件 | 收益 | 代价/判断 |
| --- | --- | --- | --- |
| 保持当前实现，仅补验收 | 近期没有新物品需求 | 保留已获得的检查能力，减少架构改动 | 定义分散仍存在；是合理选项，不代表前期投入失败 |
| 用真实物品任务推进最小规则集中 | 近期有两类真实内容需要开发 | 能测量重复接入成本，并减少确有共性的错误 | 推荐方向；每次只集中一条已证实规则，容许得出“不抽取”结论 |
| 建完整通用物品平台/插件系统 | 有明确多个消费者、稳定外部契约与维护资源 | 理论上可提高批量内容复用 | 当前证据不足；增加迁移、协议维护和测试组合，暂不建议 |

不继续抽象的后果主要是仍需手动维护多个接入位置，而不是现有 Mod 必然失稳。继续过度抽象的代价则可能是新增物品要学习更多协议、配置和例外，简单改动反而更慢。两类风险都应纳入判断。

建议停止或缩小抽取的信号：只有一个实际消费者；只是把两次短调用包成新类；需要改变官方时机或旧档结构才能统一；普通物品和设备需要大量条件分支；自动检查维护量明显超过避免的重复工作。性能优化必须有实测热点，不以框架名称推断收益。

## 8. 如何证明第三、第四期有用

以下是建议的验收方法，不是已发生的提升，也不是本次启动的新任务。

| 指标 | 测量方法 | 当前状态 |
| --- | --- | --- |
| 新增物品接入成本 | 对普通物品与设备分别记录修改文件、独立修改位置、重复填写的身份/资源信息 | 未测 |
| 防错能力 | 对真实定义制造重复键、缺关联、错误资源名等负例，确认对应检查失败且不会无差别拒绝合法变体 | 只有身份与部分注册负例已覆盖 |
| 返工来源 | 区分需求变化、遗漏接入、引擎差异、框架使用错误；比较同类任务，避免把试玩调平衡当架构失败 | 未建立记录 |
| 故障定位成本 | 用固定故障与相同日志条件记录需要查看的文件/步骤，不只计运行时间 | 当前只有能定位模块/阶段的证据 |
| 新设备复现 | 从 GitHub 检出同提交，显式配置依赖并跑检查，记录额外手工步骤 | 待新设备执行 |
| 游戏兼容 | 同一组旧测试档验证保存、付款、普通物品、设备与容器恢复 | 待用户手测 |
| 性能代价 | 同场景、同内容、同游戏版本比较帧时间、分配、加载和长时内存 | 未测，不承诺提升 |

若完成三、四期，仅能在验收证据支持下说“接入步骤更少、某类错误有自动阻挡、新设备可复现”。仍不能保证所有旧档安全、所有机器逻辑正确或第三方兼容；这些需要持续的内容级检查与实际游玩验证。

## 9. 最终建议与证据入口

保留目前的接口和检查体系；它们已经提供可复核的局部保护。把“框架完成”定义为真实开发任务中的可验证收益，而不是将所有内容迁进统一基类。跨设备后优先补验收与环境复现，再用真实物品任务选择第三期的最小工作范围。

本报告不改变已确认的五期路线，不将候选事项自动加入开发范围；剩余实施仍按用户此前要求留待跨设备继续。
