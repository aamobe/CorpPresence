# 以工坊订阅版为基准，并从反编译结果补回源码

## 背景和问题

1.0.0 的工坊文件是从 11 月 9 日 16:22 的订阅底包定向修补得到的，底包里的一部分改动没有进仓库。结果是三处“最新版”对不上：仓库源码、工坊文件、开发机上的旧工作区。继续从仓库源码发布会丢掉底包里的功能；继续从工坊文件修补则每次都要做二进制修补。应该以哪一份为准，另外两份怎么对齐？

## 决策驱动因素

- 玩家实际在用的是工坊文件，它的行为不能因为下一次发布而倒退。
- 两台机器轮流开发，仓库是唯一的交接点，源码必须完整。
- 底包的原始源码已经找不到。

## 考虑过的选项

- 选项 1：以仓库源码为准，接受下次发布丢掉底包里的改动。
- 选项 2：继续以工坊文件为底包，每次修复都做二进制修补。
- 选项 3：以工坊文件为基准，把它反编译后与仓库源码的编译产物对比，把缺的改动补回源码。

## 决定

选了选项 3。它让源码重新成为唯一来源，又不改变玩家手里的行为。

### 后果

- 好：以后可以直接从源码构建发布；另一台机器拉取仓库就能得到完整代码。
- 好：差异是逐文件对比出来的，范围明确（五处）。
- 坏：跑轮发电机那部分代码是从反编译结果整理的，局部变量名是反编译器起的，原来的注释无法恢复。
- 坏：重新编译的文件与工坊文件不是逐字节相同，一致性只在反编译后的代码层面确认。
- 后续：下一次发布前需要在游戏里实测跑轮发电机（新建、扩容、读旧档）和帕斯泰尔窗口。

### 怎么确认实现符合这个决定

用同一版 `ilspycmd` 分别反编译工坊文件和仓库的 Release 编译产物，逐文件比较。补回之后 125 个源文件中 124 个完全一致，剩下的 `GameResources.ResolveMenuStartupLocale` 只是写法不同、行为相同；167 张嵌入图片逐字节一致。下次怀疑源码与发布物不一致时，重复这个比较。
