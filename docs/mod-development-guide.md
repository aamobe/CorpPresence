# 从公司增强实践整理的MOD制作指南

整理日期：2026-11-08。依据本仓库的源码、维护文档和[40个问题案例](retrospective/README.md)，说明从功能设计到维护发布的工作方法。

本文不是某个加载器的通用安装教程。游戏后端、官方接口、生命周期和持久化方式不同，接入方法必须重新确认。文中的公司增强类名是可追踪实例，不是要求其他MOD照抄的框架。

## 阅读路线

- 新项目：从“确认环境”开始，按开发流程做一个可验证的小功能。
- 新增功能：先填写任务卡和边界表，再查对应源码及历史案例。
- 修复故障：先保留证据、定位首次失效环节，再选择最小改动。
- 维护发布：从基线和交付状态开始，不根据目录名猜测当前版本。

建议和约束分开使用：本仓库的明确限制见[AGENTS.md](../AGENTS.md)；项目管理模板是可采用的工作方法，不要求每个小修改都走一次额外审批。

## 一、确认环境，再选技术方案

开始修改前，记录游戏构建、运行后端、加载接口、本地依赖和当前MOD基线。

| 需要确认 | 为什么 |
| --- | --- |
| 游戏版本与程序集 | 同名方法可能换参数、重载或调用时机 |
| Mono、IL2CPP或其他运行环境 | 决定工具和接入方法，旧Demo结论不能直接沿用 |
| 官方MOD接口或实际使用的加载器 | 不为已有官方接口重复安装另一套加载器 |
| 本地SDK与游戏引用 | Runtime不等于SDK；接口引用存在不代表行为兼容 |
| MOD提交、清单和已安装文件 | 本地工作区可能含草稿，线上与源码也可能曾经分叉 |
| 日志来源与时间 | 旧日志不能说明当前二进制的问题 |

公司增强当前使用官方`IMod`、Harmony及Unity组件，目标`netstandard2.1`，构建需要.NET 8 SDK或更高版本。其他MOD是否适合这个组合，应由实际环境决定。

没有确认环境之前，不用“换注入器”“改权限”“换加载顺序”代替根因分析。相关反例见A01、D03、D05、D06。

## 二、把需求写成玩家可观察的行为

先回答：玩家从哪里进入、放入什么、付出什么、何时得到什么、什么情况下应该拒绝。

以香水功能为例，完整路径是：会员入口→订购花种/设备→次日交付→种植→原版化学处理→材料分离→血液提取→合成→保存读档。只完成一个机器按钮，不能认为整条产线已经完成。

需求中至少交代：

1. 玩家入口与开放条件，普通/特殊模式是否不同。
2. 输入、输出、费用、时间、数量及限购口径。
3. 失败提示和失败后应该保留的内容。
4. 旧存档、已有物品、已付款订单如何继续。
5. 本次不改变的原版规则及相关功能。
6. 验证方式和本次不执行的操作。

“只改说明”“提高可读性”“整理目录”不自动包含数值平衡、物品ID变化或运行时重构。变更影响超出原范围时，明确指出变化，不悄悄扩大实现。

## 三、先划清边界

### 原版、MOD和第三方各负责什么

| 范围 | 本项目的处理原则 | 应避免的越界 |
| --- | --- | --- |
| 原版交易、液体、分类和库存 | 优先调用原版API，保留合法规则 | 为了卖出一件自制物品强制所有顾客接收 |
| MOD新增物品/成分 | 用独立身份，只在明确ID和场景下处理 | 拿普通水瓶作模糊匹配，误迁移原版物品 |
| 原版成长与阶段形状 | 原版已负责的流程不重复接管 | 同时用原版Tick和自建时钟加龄 |
| 共享Harmony入口 | 写清触发条件、返回语义和副作用 | 钩在全局入口却没有自己的身份过滤 |
| 第三方MOD | 根据具体证据做局部适配 | 直接改对方文件、覆盖对方工厂或吞掉其全部行为 |
| 资源/事件/回调 | 谁创建谁记录拥有权，按仍持有的权限释放 | 停用时把共享委托设空，Destroy借用图集 |
| 玩家存档与财产 | 保留原记录和已完成业务，只做必要迁移 | 为“修复”直接清档、清缸、重置会员或补发整单 |
| 发布与外部账号 | 按用户授权处理指定目标 | 上传代码时顺手改工坊简介、标题或公开个人日志 |

本仓库尤其要求普通水及原版顾客判定保持原版处理，见[兼容约束](maintenance/compatibility-and-regressions.md)。这是明确的项目边界，不是说MOD永远不能扩展液体；扩展必须限定对象、状态和影响范围。

### 每个修改都回答四个问题

- **影响谁**：具体物品ID、机器、人物、模式或存档会话是什么？
- **何时生效**：生成、加载、首次操作、跨日还是每帧？
- **谁有权处理**：能查询到物品是否就有权取走；能使用资源是否就有权销毁？
- **如何撤销或继续**：失败、停用、读档和更新后会留下什么？

答不清时，先做只读追踪或最小复现，不靠全局补丁扩大命中率。

共享补丁还要尊重原方法是否已经被其他前缀跳过。例如原版操作没有执行时，自己的前置逻辑不应照常扣耗材；固定报价与其他倍率后缀也需要检查先后语义。仅仅修改同一方法，不足以证明有冲突或无冲突。

## 四、以最小完整流程建立实现

先完成一条可以走到底的路径，再扩展商品、设备或剧情。公司增强现有分工可作为定位示例：

| 职责 | 仓库实例 |
| --- | --- |
| 启动、版本、资源阶段 | `Main`、`GameResources`、`RuntimeLifetime` |
| 物品身份、定义和旧物修复 | `ItemRegistry`、`ItemIdentity`、`Goods`、`ItemTags` |
| 玩家入口与展示 | `CompanyWindow.*`、`MenuLabels`、`L` |
| 目录、报价和提交 | `Company`、`CatalogEntry`、`Services.Orders` |
| 业务交付 | `CompanyVisitors.Deliveries`、`OrderContents`、`Crates` |
| 生产与共享出料 | `Perfume.*`等产线、`ProductionOutput`、`MachineUpgrade` |
| 会话、保存和清理 | `SaveBinding`、`StoreSession`、`Cleanup` |

完整位置见[源码地图](源码地图.md)。为其他项目拆模块时，按真正不同的责任划分，不为了模仿目录数量造空层。

例如新增一种电话商品，至少核对目录注册、真实生成、报价、门槛、付款、订单保存、配送箱、送货人、签收和额度核销。博士漏注册配送箱的案例B08，说明“入口可见”不是完成标准。

## 五、启动、资源和停用是一条生命周期

### 资源就绪必须有可检查条件

安装补丁、读取静态字段或发布工厂都可能触发游戏类型初始化。等若干秒不能证明本地化表和资源已经就绪。

公司增强将核心接入和资源阶段分开，检查本地化初始化、对应语言和表数据，再接触液体、植物等类型。静态初始化失败后反复catch不一定能恢复，需要识别不可在同进程重新初始化的情况。

### 注册之前就考虑失败释放

每个步骤写出取得什么、部分失败会留下什么、如何释放。释放动作应能覆盖“刚完成前半段就抛错”，不能只为全部成功的路径登记清理。

共享回调需要考虑前任和后来接入者；借用对象与自建对象分别管理。不要把“逆序释放”称为任意游戏副作用都可回滚。相关案例A02—A04。

## 六、存档设计先保护已有数据

### 稳定身份

物品ID、状态键、库存槽顺序、资源名及程序集身份可能成为旧档依赖。改显示名不等于可以随便改ID；把液体物品改成材料时，也不能不加区分地复用旧ID。

### 会话归属

持久runID不等于当前内存对象身份。读同一个档，玩家、数据字典、原始记录或根状态仍可能替换。延迟回调执行前必须核对它是否仍属于当初的会话。

### 无效记录与旧字段

反序列化成功后检查必要结构。区分旧版本省略字段、合法空集合、显式null和真正损坏数据。保护原字符串及写入权限，不把可供展示的默认状态当作可以覆盖保存的有效状态。

### 迁移可重复执行

迁移应限定旧版本/旧身份，带必要的版本标记，并保留玩家改造。先说明不会覆盖什么，再验证第二次执行不再改变数据。

最少考虑：新档、旧档、同档重读、换档、已有已付款业务、迁移中断、满库存及卸载清理。相关案例A05—A10、C07—C08。

## 七、业务提交不要假装具有完整事务能力

推荐检查顺序：

```text
读取并确认当前会话
  → 校验资格、物品、数量和额度
  → 固定报价、随机结果、返还/交付明细
  → 检查资源、空间和记录可写性
  → 执行不可逆操作
  → 按实际完成量提交状态
  → 单独处理提示、音效和日志
```

这是一条思考顺序，不是能机械套在所有游戏API上的实现。原版销毁、付款和放置可能在回调抛错前已经产生副作用；必须先查API实际语义。

### 成功以事实为准

- 生成了对象，不等于对象已经落地。
- 落桌函数抛错，不等于对象一定没挂接。
- 堆叠后源对象没有parent，不等于件数没进入目标库存。
- 发钱后提示音失败，不等于现金没发。
- 付款委托异常，不等于可以安全再走普通现金补扣。

失败重试只处理余量，不重抽已确定内容，不重发成功返点。购物车和换货结果在付款前固定；失败不占额度。结果不确定时明确记录，不按异常类型自动推断退款或再扣。

不要为了覆盖所有理论异常，增加跨读档永久锁定却没有恢复路径的状态。C04的持久生产暂停方案后来被撤回，原因正是它增加了玩家无法退出的故障状态，却没有提供完整回滚。

## 八、UI权限、后端规则和模式扩展必须一致

UI可以隐藏按钮和解释条件，但最终提交入口仍需校验。反过来，后端不能增加玩家无法通过界面解除的限制。

每个带门槛功能列一张组合表：

| 维度 | 示例 |
| --- | --- |
| 模式 | 普通、恶意或其他扩展模式 |
| 资格 | 未签约、低/中/高档、剧情许可 |
| 服务状态 | 未开通、有效、到期、暂停 |
| 时间 | 当天已操作、冷却未到、额度恢复 |
| 存档 | 新取得资格、旧档已有资格、更新后读取 |

对每个组合说明：是否显示、是否可提交、拒绝原因、玩家能从哪里继续。B12中黑金会员已经达标，却被没有申请入口的目录等级限制，说明新产线必须追到共用面板之后的最终模式回调。

描述“免费”时明确免哪项费用；会员免费订阅不等于商品免费。显示价、实际扣款和代金券抵扣也要一致。

## 九、数值与经济设计统一口径

先确定比较单位，再计算利润：每批、每株、每晚或每台机器。不同工段利润独立比较时，不能再把它们无条件叠加成整线利润。

每个价格标明渠道、基础价、分类/违禁规则、事件、会员及固定价例外。原料和成品都按同一可售口径处理，固定价商品不强行叠加通用倍率。

对原料采用采购价还是可售机会成本，应在表中明确；鱼按什么成长阶段和屠宰产肉估值，也要先约定。默认机器和默认种子是比较基准，不能一边用改造极限产量、一边用原版默认成本。

把电费、种子摊销、机器投入、时间与稀缺资源分开，允许标注尚未计入的项目，不将漏项包装成净利润。新分类还会改变顾客范围、拒收和售货机表现，应当作玩法变化验证。

## 十、美术和交互按最终使用状态验收

制作前区分库存精灵、人物立绘、状态差分、UI图标和宣传图；它们没有统一的尺寸、限色或缩放方法。

库存物品先锁定原生网格和占格，再安排轮廓与细节。机器顶盖、机壳和瓶身保持连续色块；生成大图缩小后要检查杂色、断线和采样变化，不能凭最近邻或16色判合格。

状态差分从同一母版派生，验证画布、原点和公共像素一致。PNG透明度、库存形状、PPU/pivot、鼠标命中及UI遮挡分开处理。更新旧占格时检查相邻空间，不直接覆盖已有物品。

本项目人物以原版显示适配和撒该风格分析为参考；这属于本项目美术方向，不能推广成所有MOD的人物标准。详见[美术规范](art/README.md)与C09—C10。

## 十一、验证分层，并写清剩余未知

| 层级 | 能回答什么 | 不能代替什么 |
| --- | --- | --- |
| 源码和差异审查 | 路径、门槛、范围和结构是否合理 | 实际引擎执行 |
| 静态检查 | 文档路径、版本字段、资源名、引用/快照是否一致 | 游戏玩法与组合兼容 |
| 编译 | 指定环境下是否能产生目标程序集 | 补丁是否触发、旧档是否完整 |
| 逻辑/替身检查 | 指定方法在受控依赖和故障下的行为 | Unity对象、真实柜台、真实保存 |
| 游戏验证 | 指定构建、档、操作和MOD组合中的结果 | 所有语言、加载顺序和长时场景 |
| 发布核验 | 成功回执、实际下载与文件比对 | 功能端到端正确 |

新功能选择能覆盖真实失败路径的验证，不为凑数量写镜像实现的断言。修复尽量用旧行为能失败、修复后能通过的场景验证；无法复现时保留诊断结论，不编造已知根因。

本仓库不自行启动游戏，是否执行游戏与自动测试遵循当前任务授权和环境。文档变更验证链接和源码未变即可，不必为了说“测过”重跑整套游戏流程。

结论示例：“静态追踪未发现新增普通水身份迁移；编译通过；未执行水商交易。”不要改写为“买水问题彻底解决”。

## 十二、项目管理：让范围、基线和进度可追踪

### 维护一个明确的发布基线

主分支、预览内容、本地实验和工坊产物分别标明状态。工作区有未提交草稿时，先隔离需要提交的任务，不整体覆盖或全部暂存。

一次提交围绕一个能解释清楚的结果。已发布源码同步和文档重组分开，是为了方便追溯；小改动不必人为拆成许多无意义提交。保留历史分支和记录，不因“清理”删除无法判断用途的内容。

### 用可观察状态管理任务

| 状态 | 说明 |
| --- | --- |
| 待明确 | 尚缺影响实现或安全范围的信息 |
| 待实现 | 范围、基线、完成条件已足够清楚 |
| 处理中 | 正在修改，可记录下一步和当前阻碍 |
| 实现完成 | 代码/素材/文案已经具备，验证仍可能未完成 |
| 已验证 | 指定验证层级和场景通过，不暗示其他层也通过 |
| 已发布 | 指定目标有成功结果，注明是否回下载核验 |
| 待跟进 | 缺现场复现、用户验收或外部条件 |

状态不必另建复杂系统；一个Issue或任务文件能准确表达就够。不要把“已编译”直接改为“已发布”，也不要把等待输入写成完成。

### 风险集中处理

变动物品ID、存档结构、支付、删除、全局补丁和共享资源时，优先查边界及历史案例。低风险文案和目录整理不要顺带重构运行时。确有跨模块依赖，先标清顺序和负责人；多人或代理协作时避免同时改同一文件或共享浏览器会话。

### 记录决定而不保留相互矛盾的“当前方案”

重要取舍写下问题、选择、原因、放弃方案及代价。方案撤回时给旧记录加明确状态和新入口，不把旧生产锁机建议与当前无锁方案同时当成推荐。

已有用户授权和偏好随任务延续。可自行判断的可逆实现细节不反复请示；缺少必要输入、扩大范围或涉及新的发布目标时，再向用户说明具体差异。当前任务未要求打包，不自动生成分发包。

## 十四、交付前按目标检查

### 本地源码或GitHub

- 修改范围和最终说明一致，无夹带的未发布素材或其他工作区改动。
- 文档、版本、资源引用和旧档规则相互一致。
- 不提交游戏程序集、凭证、登录缓存、存档、个人日志或构建产物。
- 已知问题和未实测项写在可找到的位置；远端提交与预期一致。

### 本地部署或工坊

- 已获对应操作授权，确认目标ID/路径，并备份需要替换的文件。
- 版本号、DLL、清单和资源来自同一已审阅基线。
- 不同时加载相同MOD ID的本地版和工坊版。
- 诊断工具、临时探针和本地SDK不混入正式产物。
- 记录上传/部署结果，回下载有条件则比对，无条件则明确未执行。
- 图片生成、托管、正文引用、匿名可见性分别核对；含占位符的稿件不能叫可直接发布稿。

### 当前仓库的入口

构建、静态检查与输出位置见[构建与发布](maintenance/build-and-release.md)。当前版本见[版本目录](releases/README.md)，实现定位见[源码地图](源码地图.md)，具体教训见[问题复盘](retrospective/README.md)和[证据索引](retrospective/sources.md)。

本文的通用建议来自本项目经验，不能代替目标游戏的接口文档、权限机制及分发约定。移植到新项目时先重做环境与边界确认，再选择值得复用的部分。
