# 公司增强完整内部框架开发方案

> 执行说明：按任务逐项推进，采用 executing-plans 的连续执行方式；测试安排以本文和用户当前要求为准，不套用每任务全量测试或逐项游戏验收流程。

日期：2026-11-12。状态：方案已编写，以下开发任务尚未实施。代码基线：`71fabe1`，已合并 GitHub main。

**目标：** 在公司增强内部完成一套随正式版发布的开发与维护框架，覆盖内容接入、运行生命周期、存档兼容、交易交付和故障诊断，以现有业务和一个真实新增物品需求验证，使常见扩展入口明确、异常可定位、旧档受保护、发布可追溯。

**架构：** 沿用官方 IMod、Main 显式装配、RuntimeLifetime 两阶段启动与逆序释放。物品、设备、公司及恶意模式属于同一程序集中的内容模块；接口服务于实际内部复用，不另建加载器、独立框架 DLL 或自动插件发现系统。

**技术栈：** Unity Mono、C#、netstandard2.1、Harmony、.NET 8 或更高 SDK、PowerShell 7、现有 Python 检查工具。

**规格依据：** 用户确认的完整内部框架目标，以及[总框架模块契约](../../maintenance/framework.md)、[评审修复记录](../../bugs/framework-review/followup.md)。本文是后续开发的当前执行入口；旧分期文档作为历史证据保留。本文不表示所有旧建议必须照搬。

## 一、边界与完成目标

| 范围 | 目标 | 最终验收依据 |
| --- | --- | --- |
| 生命周期 | 模块明确获取、登记、撤回、释放和失败状态 | 启动失败回滚，清理失败隔离，官方停启不重复登记；不承诺原版不支持的热卸载 |
| 内容接入 | 普通物品、设备、容器共用定义、身份与注册规则 | 冲突被拒绝；创建与恢复分别验证；不破坏既有 ID、槽位或玩家改造 |
| 状态与存档 | 区分进程级、启用期和存档期状态 | 依赖齐全的两个测试档不串状态；迁移可重复执行；损坏记录受保护 |
| 公司与交易 | 特殊规则归内容，通用流程负责校验、付款与交付 | 拒绝不扣款，成功仅扣一次，配送失败重试只补余量，UI 与提交校验一致 |
| 诊断与维修 | 正式版也有可稳定获取的只读排障信息 | 版本、模块、补丁、存档绑定、两类故障可查询；采集不稳定不隐藏运行期故障 |
| 验证与发布 | 源码、构建、测试记录、发布物对应明确 | 正式身份、基线检查、权限检查、可复现性证据和上一版回退资料齐备 |

全局约束：

- 框架融入公司增强正式版；维护构建只增加维护入口，不复制业务实现。
- 不改已发布物品 ID、存档键与既有槽位顺序；需要新增槽位时只追加。
- 谁创建谁释放，借用资源不销毁；不得为消除缓存而破坏原版 UI 仍持有的 Sprite。
- 不以扩大占格覆盖其他物品，不以重置订单、清档或整单重发解决兼容问题。
- 不因为目录或文件变短就宣称依赖隔离；不以文本类型名统计作为强制依赖门禁。
- 开发不要求发布、部署或反复启动游戏。实际上传工坊另按用户授权执行。
- 本文不授权丢弃未提交修改或改写已推送历史。

## 二、测试节奏：开发阶段不进行非必要测试

**用户明确要求：开发阶段不进行非必要测试，留到最后统一测试。** 本方案据此调整执行节奏，而不是每完成一个小任务就让用户进游戏。

### 开发期间

1. 以源码核对、差异审查、必要编译为主。纯文档修改只检查内容与链接，不构建游戏工程。
2. 不在每次改动、每个提交或每个阶段重复跑 Check-Maintenance、完整权限扫描、全量本地化和游戏验收。
3. 不反复部署 DLL，不要求用户为结构拆分、命名整理等低风险改动进游戏。
4. 需要补充的回归用例可随实现编写，集中到最终测试；不能把未运行用例记为通过。
5. 仅在下列情况立即运行最小定向检查：必须复现才能确定根因；修改付款、物品身份、迁移或释放等高风险逻辑，需要先确认不会破坏既有契约；编译或已有检查暴露阻断问题。
6. 每次提前测试应记录“要排除的具体风险、所选检查、结果”。风险不明确就不追加测试；定向检查足够时不扩大为全量。
7. 自动触发的远端轻量 CI 可以正常运行，不为每个本地小改主动反复推送或重跑 CI。
8. 已通过的阶段检查保留证据，除非后续改动影响该范围，不机械重跑。

### 最终统一测试

开发范围完成后冻结候选源码，集中执行自动检查、独立审查和一次有顺序的游戏验收。发现问题先定位修复，再跑受影响用例；涉及跨系统公共逻辑时才扩大回归。最后一份发布候选必须有覆盖其最终代码的有效证据。

**“最后统一测试”不等于最后才考虑正确性，也不等于所有功能都可免测。** 对用户选择跳过的项目明确记为未覆盖；不以原版负责部分流程为理由宣称 Mod 自己的交易、持久化或回调已经验证。

## 三、阶段一：补齐可靠性、诊断与发布能力

### A1 故障报告完整性

- [x] 修改 MaintenanceDiagnostics / MaintenanceSnapshot / MaintenanceFormatter：存档采集不稳定时，仍保留可独立读取的运行期故障；会话数据标为未知，不混入旧档故障。
- [x] 报告区分运行期与当前存档故障，保留有界容量、只读采集和去敏规则。
- [x] 在 MaintenanceChecks 补充不稳定快照、会话切换和采集失败用例，按风险做必要定向验证。

### A2 补丁登记覆盖

- [x] 核对 RatWheelGenerator.Install 的四个直接 Harmony 调用，接入 PatchInstallation；保留 priority、前后置方法及原版签名。
- [x] 区分可缺省补丁与必需补丁；记录失败不等于允许带着不完整功能继续运行，明确各自失败行为。
- [x] 核对其他直接安装点，补齐缺失目标、安装异常和成功计数，不单纯替换字符串。

### A3 稳定的发布版诊断入口

- [ ] 沿 Host → MaintenanceConsole → Capture → 日志逐段定位维护热键间歇无报告的问题，不先假设是用户操作失误或 Host 被销毁。
- [ ] 为正式版提供明确、主动触发的只读报告入口，优先接入现有配置或面板；保留维护版快捷键作为开发辅助。
- [ ] 报告不创建物品、不修改订单、不读取完整存档正文，不新增不必要的文件或网络权限。
- [ ] 更新维护手册，说明触发位置、成功反馈、报告字段以及如何辨认对应版本。

### A4 构建、源码归档与正式身份

- [ ] 修正 Check-BuildIdentity.ps1：缺少自身 Git 信息时验证 dev+unknown 并继续，不能误用父仓库提交。
- [ ] 在 BuildIdentity.targets、Main.Version 和发布检查中增加显式发布构建路径：校验干净工作区、当前提交的正式版本标签及清单版本一致；不满足条件拒绝发布构建。
- [ ] 发布版本不带 dev/dirty/unknown，源码提交仍可追溯；开发构建继续保留当前标识，不能用覆盖参数伪造身份。
- [ ] 固定比较条件后，在两个目录构建同一提交，检查 SDK 实际确定性设置和路径影响；必要时增加 PathMap 等设置，记录 SDK、引用程序集和产物哈希。没有证据不宣称跨机器可复现。

交付：可靠的故障报告与补丁记录、可用的正式版诊断入口、开发/发布身份规则和源码归档检查。开发完成状态与最终验收通过状态分开记录。

## 四、阶段二：完善内部接入与状态边界

### B1 状态与模块归属

- [ ] 核对 Main、RuntimeLifetime、RuntimeUpdates、Malice.Install、SaveStructure 和诊断模块列表，列出每个模块的入口、状态作用域及释放责任。
- [ ] 对确有重复或遗漏风险的接入点使用具名登记/租约；公司列表、存档校验、诊断状态分别选择最小可行方案，保持现有顺序与失败语义。
- [ ] 不把所有直接调用机械改成委托，不在只有一个用途的地方引入通用注册中心。
- [ ] 建立状态归属表，允许记录有证据的进程级资源豁免；不把静态集合的存在本身当成泄漏。

### B2 商品与交易边界

- [ ] 从 CatalogEntry、Services.Orders 现有仓库等特殊商品出发，收拢价格、限购与资格规则，避免通用函数继续按商品 ID 增加分支。
- [ ] 明确策略输入、无策略默认值、拒绝行为及异常处理；同一规则服务 UI 展示与最终提交。
- [ ] 保留真实 Pay、订单与交付流程。不可逆操作前完成准备；不借重构改变现金/代金券顺序及余量重试语义。

### B3 公司页面状态

- [ ] 以现有页面为迁移试点，把购物车、分页、选中项等收归对应页面对象或明确的状态单元。
- [ ] CompanyWindow 保留窗口框架、输入、拖动和分发；页面提供绘制/重置入口。
- [ ] 明确关闭、切公司、换档各自清理哪些状态，避免一次清理抹掉其他仍有效状态。
- [ ] Hooks 现有分部整理保留；只有业务职责清楚时再将处理方法迁入所属类型，不做为缩短文件而增加转发层的改动。

### B4 物品、设备与旧档边界

- [ ] 保持 DefinitionSet、ItemIdentity、ItemRegistry 的分工，检查新增普通物品、设备、容器的完整接入清单。
- [ ] 单独诊断旧罐装机缺角：当前定义为完整3×3，实测旧实例可在缺角放1×1物品；原因尚未确定。若需要迁移，必须检查位置冲突、保持旋转/内容/改造，并保证重复执行安全。
- [ ] 单独诊断缺依赖存档中的 painblock 创建失败；与其他 Mod 缺失警告分开，不能直接归因或将损坏档当作正常跨档用例。
- [ ] 测试源码链接仅在实际阻碍拆分时调整，优先真实实现或编译后内容检查，不强行合并不同业务的替身。

交付：明确的状态归属和接入契约、已迁移的真实业务路径、需要保留的直接依赖及理由。外部 DLL API、页面全部重写和编译器级依赖守卫不作为本期强制目标。

## 五、阶段三：真实需求验证与最终统一验收

### C1 真实内容试点

- [ ] 接入用户随后提供的一个真实物品需求，走通定义、身份、获取、交互/加工、恢复、诊断和检查。
- [ ] 记录必须修改的公共文件、重复规则和缺失入口；优先做到内容变更集中于所属模块，不设脱离实际的“公共文件零修改”指标。
- [ ] 若真实需求尚未提供，先用现有普通物品、设备、容器验证接入说明；“真实新增需求收益”保持待验收，不虚构玩法或宣布该项完成。

### C2 自动检查与审查

- [ ] 候选范围冻结后执行 Check-Maintenance、Check-Portable；检查入口改变时执行其失败契约检查。
- [ ] 按改动范围执行必要专项、身份发布门禁和两种构建的官方权限扫描；已被统一入口覆盖的检查不另重复。
- [ ] 确认正式/维护构建差异仅为预定的维护能力；发布构建版本、清单、标签和源码身份相符。
- [ ] 做一次最终独立审查，清除阻断项，明确保留风险和未覆盖范围。

### C3 集中游戏验收

- [ ] 先备份并确认依赖齐全的测试档，记录游戏版本、源码提交、配置与实际 DLL 哈希。
- [ ] 按一次连续流程安排：主菜单报告 → 正常旧档加载 → 面板与语言 → 真实物品/设备/容器 → 交易与交付 → 正常双档隔离 → 官方停启 → 非维护/发布候选恢复。
- [ ] 覆盖拒绝不扣、成功单扣、余量不重发和迁移不损库存等重要路径；旧记录不能替代候选构建受影响路径验证。
- [ ] 前期证据可保留参考，但不能将旧构建、损坏档或用户未实际执行的步骤计为本次通过。
- [ ] 每项标明通过、失败、未覆盖或环境不满足；必要项未完成时，不宣称框架完整验收。

### C4 发布与交接

- [ ] 更新接入说明、源码地图、维护手册、变更日志和发布记录，确保新开发者从一个入口能找到规则。
- [ ] 发布前核对候选产物与已验收产物身份，保留上一版文件和回退步骤；准备分发与实际上传按用户授权执行。
- [ ] 游戏目录当前部署、未提交/未推送、未关闭问题分别记录，不能将 GitHub 同步视为工坊发布。
