# 物品开发工具与分类参考方案

日期：2026-11-12。状态：范围与设计方案，未实施工具。以当前 d16f9d8 源码及本机原版程序集核对为依据。用户要求先列清各类别需要什么，再开发仓库内工具；不继续扩建运行时框架。

## 目标与交付边界

工具位于tools，不编入DLL，不在玩家机器运行。一次填写确定性数据，生成可审阅的接入修改；复杂行为提供完整需求表、实际源码参考、待实现清单和检查选择。不能把“生成成功”显示为“物品可用”。第一版只为普通静态商品自动完成接入；其余类别必须有详细参考，但未经验证的复杂逻辑不得生成成品实现。

交付包括：命令行工具、带版本的JSON输入、每类示例输入、每类参考说明、变更预览、适用检查清单。继续使用现有Goods/ItemIdentity/GoodsText/公司目录，不建立第二套运行时配置或注册中心。

本方案是类别和工具契约设计。复杂类别的原版字段/API仍需按下列核验项完成证据表后，才可升级为可执行生成模板；不能用未核实的字段名填满代码。

## 所有类别共用的信息

1. 身份：唯一GoodsKey、独立ID、创建基底或独立Shell、旧身份是否涉及迁移；只追加，不重建已有身份基线。
2. 表现：中文/英文名称、描述、用途、稳定键、俄法文翻译或明确回退；原生尺寸素材、图集、状态图、占格及旋转。PNG大小、库存占格、鼠标区域分别登记。
3. 经济：基础价与实际报价、分类和禁运属性、公司/会员门槛、限购周期、单份数量、获取方式（目录/加工/剧情）。价格与资格沿现有后端复核。
4. 生命周期：注册依赖、首次创建、读档恢复、每帧/每日/交互回调、卸载；每个状态只有明确的写入者，不重复接管原版流程。
5. 状态：字段/标签/单位/默认值/范围/归属/保存载体/何时刷新/迁移规则。区分原版持久状态、模组持久状态、只读派生值和可丢弃缓存。
6. 操作：输入条件、成功效果、消耗、输出、失败后保留内容、重复调用行为；校验和输出准备在扣款/扣料之前。
7. 证据：参考提交与方法、适用游戏程序集指纹、代码检查、仍需实机确认的边界。参考不等于推荐完整复制，更不代表每个分支都已实测。

## 植物：参考必须覆盖的细节

- 区分种子物品、PlantDefinition、活植株表现、收获物；每个ID及关系显式列出。
- 状态图至少描述未种植、种植后生长、可收获、收获后/多年生下一轮、失活或死亡（是否存在及触发条件以原版为准），不能凭经验发明原版阶段。
- 每个生长周期列出水量、水质、营养、污染、健康对进度目标和产量的影响，以及无资源、满输出时是否结算。
- 当前CropHealth按健康调整成熟目标，并同步种子与机器进度；这是现有模组规则，不当作所有植物的原版公式。说明原版回调后可能覆盖种子进度、机器是进度来源的时序。
- 基因表：ID、等级、默认值、互斥、上限、施加对象、作用阶段、是否可被玩家移除或改变、收获继承和保存位置。油花的不育与多年生、芳香物质、potent/weak对新增花浆量的影响作具体案例。
- 新建默认基因只在首次创建赋予；旧档按版本定向迁移，不重刷玩家基因。收获回调不重复套工厂基因，不对已有其他成分再次乘倍率。
- 多年生下一轮进度、收获种子和收获物数量分别核对；生长/基因/成分状态跨保存重载保持。
- 代码检查优先覆盖边界健康、成熟目标变化、收获回调一次性、迁移幂等及玩家改造保留。实机仅保留完整生长收获与重载，特有基因选一个代表组合。

## 液体系统：采用原版统一模型

不能按“普通水”和“特殊液体”建两套独立运行模型。必须区分以下层次：

- `water`：Liquid表中的一种成分。
- `Liquid.Liquids / LiquidDict`：所有注册成分，包括粗异构蛋白、异构蛋白和花浆/基底油。
- `LIQUID_CONTAINER_TAG`及各`CURRENT_PART_*`：容器能力及各成分量；当前接口以微升存储，容量输入有毫升接口，换算1000。
- `WATER`：原版动态商品分类，不等于容器里只有water成分。
- `CATEGORY_WATER_PURITY`：真实/表观纯度、鉴定与展示；不等于物品名称。
- 水纯度、异构蛋白纯度、化学产品纯度分别是不同指标，禁止都写成含义不明的Purity。

### 本次原版源码已核实

核对程序集SHA256：`725CB999D019DFF1FF31BED353C7F9BB8D81A7605A15DE1F80F5A3A6CF7B1D05`。反编译材料留在仓库外，不提交原版源码。

1. `WaterHelper.GetWaterPurity`：仅对液体容器，按water量乘10000除以全部注册成分量之和；总体积为0时返回0。
2. `GetTotalVolume`遍历Liquid.Liquids累加currentPart；自定义成分注册会影响该计算。没有注册的保存标签不会被这段总量代码计入。
3. `UpdateContainerGoodType`对具有液体容器基础价格标签的对象：空容器移除WATER并设HOUSEHOLD_GOOD，非空相反。不应硬编码所有液体永远WATER，也不能以自定义材料名排除这条原版规则。
4. `InitLiquidContainerItem`会将当前注册的各成分量置零。因此只能在合适的工厂初始化阶段调用，不能在已恢复内容上再次调用而不保护状态。
5. `WaterFeatureHelper.OnLiquidChanged`更新分类、真实/表观等级、价格并清除试纸标记；表观纯度不一定等于真实纯度。调用点还依赖Unity对象，离线算比例通过不等于真实刷新通过。
6. `SaveManager.EncodeNode`保存state克隆及itemTypes；Decode先走目录工厂，再恢复state/modifiedState、分类、价格和形状。不能推断原版完全不支持保存自定义成分，也不能只看modifiedState就声称已持久化；后续注册顺序、标签写入及修复动作必须继续核对。
7. `StoreClient.IsClientBuyingThisItem`先执行拒收判断，再检查顾客收购ID、标签及偏好；WATER分类正确只是交易链的一部分，不保证每个顾客收购。顾客具体拒收条件还需对应需求核验。

### 银血必须说明的具体关系

银血配方当前为50mL：粗异构蛋白10、water28、protein5、fat3、microbe2、organic_waste2。按上述原版公式，初始水纯度为5600/10000（56%）；这是配方静态计算，不是本次实机测量。反应后成分变化会影响原版等级与估值，异构蛋白纯度则按corp_isomer量除总量计算。

`Services.IsWaterSaleItem`用于模组售水奖励，要求IsGameItemType(WATER)且原版水纯度大于0；它不是原版顾客收货的完整判据。完全不含water的混合物即使具有WATER分类，也不满足该奖励入口。

发现需要先做定向验证的风险：银血/异构蛋白瓶定义Types仅MEDICAL；`ItemTags.AfterDecode → Repair → Apply`清除并重写商品类型，没有在该路径重算液体动态分类；新建灌装却会调用OnLiquidChanged写入WATER。可能出现读档后分类与新建不一致。证据等级为源码路径风险，尚未实机复现，未定为历史售水故障根因。本方案不顺手修改它；在液体参考被标为可复制前必须用相关代码检查验证并处理，不能把现有银血整段当作已验证模板。

## 养殖、水产原料和水产食品的区别

活体物种是原版养殖状态机对象：种类、年龄、阶段、健康、饲喂、缸内位置和形状等参与TickTank。已知银血的年龄/饲喂/成长/移动归原版；模组仅扩展自己的血量和适应规则，禁止额外按日加龄。参考需写清每阶段占格与精灵，成长空间不足、满缸、移动边界、出缸、断电、水环境、死亡及读档；繁殖或基因若原版不支持就标不适用/待设计，不从植物模板搬入。

死亡整鱼、切片、鱼肉糜不是同一个配方输入。海鲜封装机的整鱼路径要求已宰杀、未切片、亚成年普通罗非鱼；这只是该配方的约束，不能泛化为所有水产。每份参考列明识别方法、物种、活死、阶段、整条/切片、数量/重量、堆叠和所有权，避免按名字或宽泛分类接受活鱼或错误阶段。

鱼罐头和蟹味棒属于加工成品：继承哪些成分/品质必须明示，不能自动带入活体成长状态。配方用水、塑料、供电、可重复使用材料、批量和出料空间分别计算。准备全部输出后再消耗；部分成功按实际产出结算；失败不能扣掉整批原料。

养殖设备本身再组合设备与容器参考：缸的槽位、体积和电力不同于生物的属性。装进缸不等于被原版正确登记为养殖对象。

## 每份分类参考的统一结构

每类文档都包含：用途与不适用范围；一条完整现有案例链；按文件列出的接入点；字段字典与单位；状态转换表（触发、守卫、变更、消耗、输出）；原版/模组所有权表；新建/读档/迁移差异；获取使用加工销售退出的完整路径；两个已知失败反例；最小输入示例；代码检查和必要实机项目；证据等级与未核验项。

参考以真实源码链接为主，避免复制几百行很快过期的实现；短片段只解释关键时序。15类分别建文档；液体追加成分、容器、保存交易三个专题，植物追加基因与生长专题，养殖追加阶段与原料转换专题。没有已验证案例的类别明确标示，禁止伪造“完整示例”。

## 工具设计

拟新增 `tools/ItemAuthoring/`：`item-authoring.ps1`入口、`schema.json`输入规则、`templates/`静态片段、`examples/`分类输入。参考文档放 `docs/maintenance/item-authoring/`，README索引链接每类。采用现有PowerShell 7与.NET SDK，不添加玩家端依赖；如结构编辑需要语法解析，应优先使用SDK已有Roslyn，不对任意C#文件做无约束字符串替换。

输入首版包含schemaVersion、kind、key、identity、names、description、art、shape、value、types、acquisition，以及各复杂类别的requirements。不得接受任意可执行代码字段。kind为普通静态商品时才允许完整自动接入；其他类型输出草稿和明确的未实现项目，不能混入正式注册表制造半成品。

拟提供命令：`-Spec <json> -Preview`（默认）、`-Spec <json> -Apply`、`-Spec <json> -Check`。Preview只生成差异与清单；Apply先验证所有目标和冲突，保留原文件字节备份，成功后才提交整组修改；中途失败恢复本次改动，保留此前用户修改。Check选用既有检查，不隐式部署、启动游戏、提交或发布。

路径必须限制在指定仓库；ID限定允许字符，名称/描述按C#/JSON/CSV分别转义；拒绝路径穿越、ID/文本键/目录重复、基底不明确、占格非法及缺图。旧身份基线只读。相同输入再次运行不重复添加；文件并发变化时停止应用并给出清楚原因，不能覆盖用户改动。

输出记录每项文件、生成/更新原因、仍需人工实现项目、翻译回退和推荐检查。只有全部登记完整且对应检查成功才标“代码接入检查通过”，不写“游戏可用”。

## 分阶段执行与验收

## 方案评审重点
