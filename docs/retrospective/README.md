# 公司增强开发问题复盘与反例目录

整理日期：2026-11-08。目的：保存公司MOD开发中实际暴露的问题、被撤回的方案和验证教训，供后续MOD开发查阅。

现存可核验材料最早覆盖0.3.3.2审查，延续到0.9.9香水线会员修复。没有材料的更早版本不补写。本文收录40个案例；同一问题可能跨多版反复出现，不按版本号算成多次独立事故。

## 如何理解证据

- **现场记录**：有当时玩家操作、截图或日志支持。只证明记录覆盖的场景。
- **历史复现**：历史文档记载在隔离程序集、替身接口或故障注入中复现。不是本次重新运行，也不等于Unity实测。
- **代码确认**：能从实现或差异确认路径，但没有对应现场复现。
- **设计/流程反例**：方案被撤回、交付方式不合适或资料表达错误；不冒充已上线的程序崩溃。
- **未闭环**：有反馈或局部处理，但原问题归因、真实游戏验收或发布核验仍缺证据。

“有修复代码”“编译通过”“用户实测通过”“工坊上传成功”“线上文件回下载一致”是五件事，不能相互代替。每例的状态以正文和[证据索引](sources.md)为准。

## 问题总汇

### A. 启动、资源与存档

详见[启动与存档案例](runtime-and-saves.md)。

| 编号 | 问题 | 应避免的做法 |
| --- | --- | --- |
| A01 | Demo与正式版运行环境混用 | 沿用旧注入器、旧日志或旧测试工具判断新版本 |
| A02 | 资源未就绪触发水名/液体静态初始化 | 用固定延时或不断catch重试替代就绪条件 |
| A03 | 部分安装失败后留下半注册状态 | 只在全部成功之后登记释放动作 |
| A04 | 停用时删除其他MOD回调或借用资源 | 把“我用过”当作“我拥有” |
| A05 | 存档入口意外构造玩家 | 在菜单、载入中直接访问惰性Instance |
| A06 | 相同RunId下旧状态覆盖新记录 | 只用runID判断当前存档会话 |
| A07 | JSON能解析但内部集合为空 | 用默认状态静默覆盖异常原记录 |
| A08 | 旧对话/签收操作新存档 | 闭包只抓住订单，没有抓住会话归属 |
| A09 | 夜间重入、重复扣费或日志阻断后续 | 一个大try包住所有公司，或把日志算进提交 |
| A10 | 卸载清理误删机器内原版物品 | 只检查第一子库存就销毁父机器 |

### B. 订货、交付与交易

详见[订货与交易案例](orders-and-trading.md)。

| 编号 | 问题 | 应避免的做法 |
| --- | --- | --- |
| B01 | 商品生成失败仍删整张订单 | 把循环结束当作交付成功 |
| B02 | 部分交付/发钱后异常导致重发 | 重试整单，不记录已经成功的部分 |
| B03 | 工厂短暂失败永久变成1元报价 | 将失败结果缓存为有效0基价 |
| B04 | 付款后才发现数量、金额或明细无效 | 把准备工作放在不可逆扣款之后 |
| B05 | 付款委托异常二次扣款、免订阅仍收费 | 不区分拒绝、代付完成和结果不确定 |
| B06 | 盲盒重抽、实验室预约清单变化 | 对已经确定的业务结果再次随机/生成 |
| B07 | 箱体放不下、堆叠后误判没交付 | 只查是否有空位，或只查源对象归属 |
| B08 | 博士订单反复顺延 | 增加目录入口却漏注册完整配送链 |
| B09 | 展示分类与原版商人实际判定不同 | 直接改列表，不同步游戏状态标签 |
| B10 | 人物互相阻塞、读档重抽来访日期 | 用全局队列和临时随机替代独立预约状态 |
| B11 | 原料/成品及标签加价口径不一致 | 使用基础价代替实际交易价，漏掉固定价例外 |
| B12 | 黑金会员仍锁香水目录 | UI按会员、后端按另一套无入口的申请档位 |

## “不能买水”必须拆开查

这不是一个统一原因的故障名。现有材料至少涉及：

1. **原版拒收条件**：滤芯作为内容物、奢侈品/危险水标签、顾客偏好。属于规则，不应强制绕过。见B09。
2. **启动及语言缓存**：动态名称与过早初始化的缓存名不一致，可能影响水类识别。见A02。
3. **公司扩展越界**：液体注册时改全局水名、通用估值补丁扩大影响面。后续选择撤回全局干预。见A02、D08及[水系统历史边界](../releases/archive/water-compatibility.md)。
4. **售水合作度漏结算**：属于公司收益记账，不等于水本身无法交易。见D03。

香水审计未发现新增逻辑重新引入普通水身份误迁移或WATER标签清除路径；这只是当时静态追踪结论，不能扩写成“所有水问题永久解决”。

## 仍不能写成“已彻底修好”的反馈

| 反馈 | 当前能支持的说法 | 仍缺什么 |
| --- | --- | --- |
| 新局失败、跨日保存卡住 | 查过状态归属、初始化、鱼缸边界等具体风险 | 原故障玩家对应版本的可复现档与完整调用链 |
| 普通水拒收 | 已有名称错配和原版拒收条件证据，已收窄MOD边界 | 指定容器/顾客/语言/组合下的交易回归 |
| 框选后只有按住的物品能拖 | 会话中用户重启后恢复 | 确定触发步骤及根因；不能据此编造修复 |
| 早期名片补送循环 | 0.3.3.2审查记载用户日志确认对应补发行为 | 更早故障根因完整材料；不补写细节 |
| “免税后307”等零散截图 | 上下文不足的历史反馈 | 原始报价、标签、事件、服务和计算路径 |
| 索拉纳会员修复上线效果 | 修复源码、编译与工坊成功回执均有记录 | 该次上传回下载比对和玩家游戏实测 |

## 今后开发前的最低检查

1. 写出谁拥有物品、状态、资源和回调，以及以什么事实确认成功。
2. 对每个不可逆操作标明前置准备和提交点；结果不确定时不盲目重试。
3. 检查UI门槛、提交校验和模式回调是否一致，尤其是后加的新产线。
4. 修改游戏共用入口时，明确自己的ID/场景边界，先保住原版流程。
5. 设计旧档迁移时，保留已有内容、进度和玩家改造，验证重复执行。
6. 分别记录静态检查、替身复现、编译、游戏实测和发布核验；缺哪层就写哪层。
7. 记录真正发布的源码、资源和文件哈希；不靠文件夹名或版本号猜测内容。

后续新问题继续使用案例编号，写明来源、根因、处理、残余风险和防复发场景；只有症状而无根因的，先放入未闭环表。
